# P4.3: A pod that scales down finishes its calls first

Added 2026-11-19. PLAN.md's row: "Drain: preStop hook, draining mark, no new runs, timeout"; done when "Scale-down
during replay: 0 interrupted runs". Decided by the user while planning (2026-11-19): option A of question 1, C of 2,
A of 3, A of 4 below.

Read in source before planning (Claude, 2026-11-19):
- llm-d-router v0.11.0 drops a pod from the picker's pool the moment Kubernetes sets its DeletionTimestamp
  (`pkg/epp/util/pod/pod.go` IsPodReady returns false; `controller/pod_reconciler.go` updateDatastore then calls
  PodDelete), long before the pod exits. Kubernetes sets the DeletionTimestamp before it runs any preStop hook. So, with
  the picker as it is: no new call, and no new run, reaches a pod once its removal starts (the "draining mark" is
  Kubernetes' own DeletionTimestamp, which the picker and the cluster panel, card 47, already read); the calls already
  on it are the only thing a drain can save; the runs pinned to it are remapped at once and lose their cache (P3.4's
  remap), whatever the pod does next. Letting pinned runs finish there needs the pod chosen and held before Kubernetes
  deletes it, which the HPA that KEDA makes does not allow: it lowers replicas and the ReplicaSet deletes at once.
- vLLM v0.31.0 (read in the pinned image): on SIGTERM the API server calls the engine's shutdown with
  `--shutdown-timeout` (`entrypoints/launchers/launcher.py` handle_shutdown). The default is 0, mode "abort": every
  running and waiting call is aborted at once (`v1/engine/core.py` _handle_shutdown, finish_requests ABORTED). With a
  timeout above 0, mode "drain": the engine keeps stepping its calls up to that long, and a call added meanwhile is
  rejected (_reject_add_in_shutdown). So today a real pod that scales down kills its calls the moment it gets SIGTERM.
- llm-d-inference-sim v1.0.0 (source, `pkg/communication/communication.go`): on SIGTERM it rejects new calls with 503
  and waits for OpenRequests (waiting + running, `pkg/simulator/simulator.go`) up to a hard-coded 30 s, then 5 s for
  its HTTP server. The pod's default terminationGracePeriodSeconds is 30. So today a simulated pod already saves calls
  that end within ~30 s; longer ones are cut. Its image is distroless (one binary, no shell, user 65532), so a preStop
  hook cannot run a command of its own in it.
- Card 38 said P4.3 might use the end-of-run signal to end a drain early. That only matters if pinned runs finish on
  the pod (question 1, option C); with calls-only drain the plugin and the end-of-run server are untouched.

Decisions (asked 2026-11-19; the user chose the first option named in each):
1. What the drain guarantees. A (recommended): the calls on the pod when its removal starts finish there, up to the
   timeout; pinned runs move at once (P3.4's remap), and the report counts them as the drain's cost. B: A, plus the
   pod with the fewest live pins is the one removed: the plugin writes the `controller.kubernetes.io/pod-deletion-cost`
   annotation, so the picker's Role gains pods patch. C: pinned runs finish on the pod: a controller between KEDA and
   the Deployment that picks a pod, marks it in the plugin, waits for its pins to end (the end-of-run signal), then
   lowers replicas. A new component.
2. Where the drain logic lives. C (recommended): one waiter for both pod kinds, a small Go program in `gateway/`
   (stdlib only) built into the picker's image, copied into each vLLM or sim pod by an init container, run as the
   pod's preStop hook: it reads the pod's own /metrics until `vllm:num_requests_running` + `vllm:num_requests_waiting`
   has been 0 for drain.quiet_seconds, or drain.timeout_seconds pass. The sim then drains as real does. A: a Python
   waiter in a ConfigMap for vLLM (its image has python3), a fixed preStop sleep of the whole timeout for the sim; every
   sim pod removal then takes the full timeout (restarts too), and the sim's done-when only shows the sleep. D: vLLM's
   own `--shutdown-timeout` and no hook; the sim keeps its 30 s.
3. How the replay forces a scale-down. A (recommended): a scripted one, like P3.4's delete: at a set time, the Ready
   pod with the most open calls by its own /metrics gets the lowest pod-deletion-cost and the Deployment is scaled down
   by one, so the ReplicaSet removes that pod; variants drain off (the pods as before P4.3, the control) then on. B:
   KEDA on remaining work with a short scale-down window set by the variant; which pod goes, and whether it had calls,
   is left to the ReplicaSet. C: kubectl delete, as P3.4: not a scale-down, the ReplicaSet replaces the pod.
4. Real pods. A (recommended): the sim done-when plus a short real check at 2 -> 1 with the recorded demo trace, drain
   off then on: the sim's control may show nothing to save (its own 30 s drain), where real vLLM's default aborts every
   call, so the real control shows what the drain prevents. B: sim only; real at 1 <-> 2 is P4.5's.

# P4.3: drain on scale-down

Goal:
A vLLM or simulated pod being removed keeps serving the calls it holds until it has none left or drain.timeout_seconds
pass, so a scale-down interrupts no run; the picker already sends it nothing new.

Interfaces / outputs:
- config, every profile, a new section:
  drain.enabled: true. The pods drain on removal. A flag so a variant can turn it off for the control (D11); on in
  every profile, since it changes no routing and only stops calls being killed.
  drain.timeout_seconds: 120, agent.llm_timeout_seconds: a call on the pod at its removal has at most that long before
  its client gives up, so a longer drain saves nothing and a shorter one may cut a call still awaited. A test holds
  timeout >= llm_timeout in every profile.
  drain.quiet_seconds: 5. The pod counts as empty once its engine has had no call for this long, so a call the picker
  sent just before the pod left its pool, still on its way, is not cut. A first guess, P3.4's settle: the picker's
  informer plus the 2.5 s the VM's clock can step.
- gateway/drainwait: Wait(read, clock, timeout, quiet, poll) polls read() (the pod's /metrics text) every poll (1 s, a
  named constant: the resolution of the drain's end; one read costs ms) and returns idle once
  vllm:num_requests_running + vllm:num_requests_waiting, summed over every series, has been 0 for quiet; timeout when
  timeout passes first. A read that fails or lacks either metric counts as busy, so a pod too loaded to answer /metrics
  is not cut. main: `drainwait install PATH` copies itself (the init container; the image has no cp), `drainwait wait
  --metrics URL --timeout D --quiet D` runs Wait and exits 0 either way (a hook's exit code does not change the
  termination).
- Charts, drain on: an init container from the picker image (tag from picker-image.sh --tag) copies drainwait into an
  emptyDir at /drain; the server container's preStop runs /drain/drainwait wait against 127.0.0.1:8000/metrics with the
  profile's timeout and quiet; terminationGracePeriodSeconds = timeout + an exit margin (values.yaml, a named infra
  wait with a comment, not a tunable: vLLM's teardown after SIGTERM with nothing in flight; the sim's after an empty
  drain). Drain off: none of this, the pod as before P4.3. The charts refuse a missing or non-integer timeout or quiet.
- make drain-check EXPERIMENT=experiments/drain.yaml, loadgen/load_generator/drain.py: per variant in order, the pool
  redeployed with the variant's drain (helm upgrade --reuse-values --set drain.enabled), the profile's routing with the
  file's rules (P3.4's set_routing), a replay in-process. At scale_down_after_seconds it waits up to
  wait_for_calls_seconds for a Ready pod holding a live pin in the picker's log, gives the one with the most (ties by
  name, P3.4's choose_pod) pod-deletion-cost -1, scales the Deployment down by one, checks Kubernetes took that pod,
  and waits for it to be gone. Changed while building (Claude, 2026-11-19): first planned as the pod with the most open
  calls by its own /metrics, which needs a third copy of the count parser (the waiter's, priority_check's) in loadgen;
  with affinity on and steps a few ms apart a pinned run nearly always has a call on its pod (card 39), and the verdict
  counts the calls running on the pod from the replay's lines, so a wrong guess shows as void, not as a pass. Then
  the profile's pool and routing come back (finally). Results beside each other in experiments/results/, stamped with
  the file's hash: the replay lines, its printed lines, the picker's log, a .meta.json, and a report per variant:
  - calls running on the removed pod at the scale-down (the replay's lines; a failed call by its run's pin, as P3.4)
    and how long the pod took to go;
  - calls in flight at the scale-down and calls sent before the pod left the pool plus the settle, each answered or
    failed with its reason (P3.4's failure_reasons);
  - interrupted runs: runs with a failed call from those two groups whose reason is not the call's deadline;
    deadline failures counted apart (one pod is left to carry the load);
  - calls the removed pod answered that were sent after the settle (no new runs: must be 0);
  - runs pinned to it at the scale-down and remapped (the drain's cost in cache, P3.4's remapped lines).
  - the picker's container restarts during the replay (P3.11).
  A drained variant passes with at least one call running on the removed pod at the scale-down, no interrupted run and
  no call answered by it after the settle; with none running there it is void, not passed. The control is counted, not
  judged. make drain-check exits 1 if a drained variant did not pass.
- experiments/drain.yaml: profile sim, routing {plugin: true, affinity: true}, P3.9b's converted trace, pattern burst,
  seed 6, the profile's 2 pods (no autoscaler), scale_down_after_seconds 125 (5 s into the first burst, when the pods
  hold queues), wait_for_calls_seconds 60, settle_seconds 5; variants drain-off then drain-on.
- experiments/drain-real.yaml: profile real, the same rules, the recorded demo trace (short runs), pattern steady,
  seed 1, 2 pods -> 1, scale_down_after_seconds 45 (runs start at 0, 22.0, 39.0 and 75.9 s, ~22 s each),
  wait_for_calls_seconds 60; variants drain-off then drain-on.

Notes:
- What the drain does not save: runs pinned to the pod lose their cache and move (question 1); a pod that fails rather
  than scales down (P4.4).
- Real pods share the GPU's two time-sliced slots: a draining pod keeps its slot until it exits, so a scale-up during
  a drain waits for it. For P4.5.
- P4.1's finding: one fresh real pod's engine counted its calls ~50 s after they were sent, place unknown. If such a
  call is in transit at the removal, the engine reads 0 and quiet_seconds does not cover it. The real check shows
  whether it happens; not handled here.
- P3.11's finding: the picker can restart under load (1 s liveness probe), failing closed; calls lost that way are not
  the drain's. The report counts the picker's restarts in the variant and names them.
- KEDA's scale-downs in P5.2 drain too, so a drained pod counts in the series while it drains; P5.2 reads
  kube_pod_deletion_timestamp to tell it apart.
- Tests first: Wait (idle at once, busy then idle, never idle, a failed read inside the quiet window, a metric missing,
  two model series summed, the timeout's edge); the charts rendered with drain on and off (helm template); the
  timeout >= llm_timeout check; drain.py's choice of pod, groups, interrupted runs, void variant and report from
  hand-written lines. Each rule line changed once to check a test fails.
