- Our own filter holds the pin, because P3.5 and P3.6 have to override it. Upstream's `session-affinity-filter` (alpha, `strategy: session_id`, source `x-run-id`) is one extra variant in P5.1, and chapter 2 cites it.
- End of run (D1): the plugin opens `POST /runs/{id}/end` on an extra port (chart: `router.epp.extraContainerPorts`, `router.extraServicePorts`). A header on the last call can't say it, since the agent only knows after the reply. The TTL stays as the safety net for a lost signal. P4.3 relies on this signal to end a drain early.
- This replay runs on real pods in one order, about 1.3 h: the claim is the hit rate, which followed the variant in both of 2026-11-08's orders, unlike generation time. It makes no latency claim; P3.7 does.

Decided 2026-11-10 with the user, while planning: the report counts, per variant, the later steps that stayed on their pod but found less than their previous prompt less 24 tokens cached (P2.4's 9 template tokens and a block's 15), so a pod that evicted a run's history does not read as a cache miss of the rule. In `experiment.py`, since `config/report.yaml` is not an allowed file here: the 24 is derived, not tuned.

Decided 2026-11-11 with the user, after the replay: affinity's hit rate was 0.807 against default's 0.821, both inside
default's range, so the criterion "above default's" is not met and is recorded so. The overall number hid where affinity
changed anything: `make experiment-compare` now pairs each run's hit rate across the two variants, over every run and
over the runs each variant moved a step in, from the CSV alone. `loadgen/load_generator/experiment_compare.py` is added
to the files allowed for it; its report already paired runs on time, and the experiment's own report prints only at the
end of a live replay. Read after the overall number was seen, which the log says.

Decided by Claude, stated to the user:
- The pin store is a map behind one mutex, with an injected clock. A pin past its TTL counts as none; every record also drops every expired pin (one pass over a few dozen runs), so no sweeper goroutine.
- PreRequest reads and writes the pin under one lock and logs reason `pinned` when the run's live pin was the chosen pod, `first` otherwise. First planned as upstream's `PluginState` handing the Filter's decision to PreRequest; dropped as more machinery for the same answer, since PreRequest sees the old pin and the pick together. A pin whose pod is not a candidate passes every candidate and is overwritten, logged `first` until P3.4 names it `remapped`. An empty `x-run-id` counts as none.
- Two new required parameters: `runTTLSeconds` (positive whole seconds) and `endOfRunPort` (1-65535). The factory opens the port itself, so a port it cannot bind fails the picker at start rather than losing every end to the TTL. The server closes with the handle's context.
- `routing-values.sh` holds the port, 9010 (the picker uses 9002, 9003, 9090), and with the plugin on puts it on the picker's container and Service, named `end-of-run`; with the plugin off there is no port. The replayer finds it by name; `agent.yaml`'s `PICKER_URL` names 9010. `run_ttl_seconds` is the profile's alone: a variant that sets it is refused, by `routing-values.sh` and by `check_routing` before the cluster is touched.
- The agent runtime's call runs only in unit tests in P3.3: every profile has `routing.plugin` false, and an experiment's variant changes the picker, not the agent's profile. Phase 4's demo profile is the first to use it.
- `set-routing.sh`'s probe carries `x-run-id: set-routing-probe`, so with affinity on it leaves one pin until the TTL. Harmless, left as is.

The risk, told to the user since P2.2b: cache hits save little time, because generation dominates. Default already scored 0.794-0.836 across its four baseline runs (P2.5 twice, Gate 2 twice) and moved only 27-43 of 243 later steps, so affinity may add only a little. That is a result to report, not a bug to tune away.

# P3.3: Task affinity

Goal:
Steps 2..n of a run go to the pod that served its first step: run-id -> pod with a TTL, cleared when the run ends. The first
step is still picked by load and prefix (the default scorers).

Depends on:
P3.2

Files allowed:
gateway/runrouter/, config/real.yaml, config/real-plain.yaml, config/sim.yaml, config/demo.yaml (routing.run_ttl_seconds),
infra/routing-values.sh, infra/helm/ (the extra port), infra/manifests/agent.yaml (PICKER_URL),
agent/agent_runtime/ (the end-of-run call, config), agent/tests/, loadgen/load_generator/replay.py,
loadgen/load_generator/experiment.py, loadgen/load_generator/experiment_compare.py (added 2026-11-11, per-run hit rate),
loadgen/tests/, experiments/affinity.yaml (new), experiments/log.md, experiments/results/,
experiments/graphs/, PLAN.md (P3.3 row), docs/task-cards/38-P3.3-task-affinity.md

Interfaces / outputs:
- Filter: with routing.affinity and a pin on a pod among the candidates, returns only that pod; otherwise every candidate.
- PreRequest: records run-id -> the chosen pod and renews its TTL.
- POST /runs/{id}/end on the picker's extra port, 204 whether or not the pin existed. Sent by the agent runtime after its
  final save and by the replayer as a run stops, only when routing.plugin is on. A failure is logged and left to the TTL
  (httpx.HTTPError only): a run's answer must not depend on it.
- routing.run_ttl_seconds: a first guess of 300, longer than the longest call (agent.llm_timeout_seconds 120) plus its gap.
- A JSON log line per decision with run-id, step, pod and reason (first, pinned).
- experiments/affinity.yaml: profile real, the converted trace, pattern baseline, seed 6, variants default, affinity.

Notes:
Tests first, table-driven with a fake clock: first step unpinned; later steps pinned; TTL expiry unpins; TTL renews on use;
end of run removes the pin; another run is untouched; a request with no x-run-id passes through. The map is in memory in one
picker pod, so a picker restart forgets pins and runs fall back to load + prefix, a stated limitation.
From earlier tasks: report stalls and the queue and KV split, not only hit rate (P2.5); a capacity effect over the KV limit can
read as a cache effect (P2.4); on a replay, a pinned step's cached_tokens should be at least the previous prompt less 24
(P2.4); on 2 pods the default picker moved 28-43 later steps on real and 10 on sim, so sim understates moves (P2.9).
