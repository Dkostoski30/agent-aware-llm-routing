# P1.2: Gateway + Gateway API Inference Extension, default Endpoint Picker

Goal:
LLM calls go through an agentgateway Gateway whose InferencePool holds the vLLM pods. The llm-d-router Endpoint Picker
(EPP), unchanged, chooses the pod, and make up / make down install and remove all of it.

Depends on:
P1.1

Phase 1 order (task cards 11-18): P1.2 -> P1.3a -> P1.3b -> P1.6a -> P1.6b -> P1.5 -> P1.4a -> P1.4b.
Gate 1 needs only make smoke and the P1.6 result, so the UI goes last.

Spike (done 2026-10-27, experiments/log.md):
Since GAIE v1.6.0 the full EPP lives in llm-d/llm-d-router; GAIE keeps the InferencePool API. kgateway dropped
InferencePool in v2.3.0, and Envoy Gateway has no native support. Decided:
- Gateway API CRDs v1.6.3, standard channel
- GAIE CRDs v1.6.2 (v1-manifests.yaml; InferencePool inference.networking.k8s.io/v1)
- agentgateway v1.6.0, chart value inferenceExtension.enabled=true
- llm-d-router v0.11.0, chart oci://ghcr.io/llm-d/charts/llm-d-router-gateway v0.11.0 (gateway mode,
  provider none), image ghcr.io/llm-d/llm-d-router-endpoint-picker:v0.11.0 pinned by digest
Fallback if the v0.11.0 EPP and agentgateway don't work together: llm-d-router v1.0.0 (made for GAIE v1.6.2),
written into versions.md as an exception to the two-week rule. Stop and ask before switching (rule 8).

Files allowed:
infra/install-gateway.sh (new), infra/helm/agentgateway-values.yaml (new), infra/helm/router-values.yaml (new),
infra/manifests/inference-gateway.yaml (new: AgentgatewayParameters, Gateway, HTTPRoute, AgentgatewayPolicy),
infra/checks/gateway_check.sh (new), Makefile (up, new target gateway-check), infra/down.sh,
.pre-commit-config.yaml (check-yaml allows multi-document manifests; user decision 2026-10-27),
versions.md, experiments/log.md, docs/task-cards/11-P1.2-gateway.md
(The vllm chart needs no change: its pods already carry app.kubernetes.io/name=vllm. No gateway setting is an
experiment tunable, so config/ is untouched.)

Interfaces / outputs:
- Release vllm-pool of the router chart creates the InferencePool vllm-pool (selector app.kubernetes.io/name=vllm,
  target port 8000, failureMode FailClose so no request bypasses the picker) and the EPP vllm-pool-epp, both in
  default. The Gateway inference-gateway (port 80) and the HTTPRoute vllm send /v1 to the pool. Works with
  replicas: 2 (real) and 1 (demo).
- The EPP runs the chart's default scheduling profile (queue, KV-cache and prefix-cache scorers); the latency
  predictor stays off and every routing flag in config stays false. Its requests are lowered from the chart's
  8 CPU / 8Gi to 100m / 128Mi; the chart's 16Gi limit stays and can't bind on this VM. P3.1 replaces the image with
  a self-built one.
- Charts are installed by digest; the agentgateway images come from its chart (as for the monitoring stack), the EPP
  image is pinned by digest.
- The gateway access log is JSON (AgentgatewayParameters), one line per request, with the upstream endpoint and the
  headers x-run-id, x-step, x-expected-steps, x-parallel-group under the D12 log keys run-id, step, expected-steps,
  parallel-group (AgentgatewayPolicy; user decision after review, 2026-10-27). P1.3b and P1.5 read them.
- The EPP runs at --v=3, the lowest level that logs "Request handled" with the chosen endpoint. Its logs are
  OpenTelemetry-style JSON (message in body, time in timestamp).
- make gateway-check: 20 short chat requests (shorter than one prefix-cache block), 4 at a time, then one with the
  D1 headers, all to the Gateway's ClusterIP from the node. Prints the requests per pod from the access log, the
  access-log line with run-id p12-check, step 1, expected-steps 1 and the EPP's last choices. Exits 1 if a Ready pod
  got none, the header line is missing, or the EPP logged fewer choices than requests.
- make up runs infra/install-gateway.sh after vllm-deploy; infra/down.sh removes the Gateway first, then the
  releases. The Gateway API and GAIE CRDs (applied with kubectl) stay; agentgateway's CRDs go with their release.

Notes:
Brick wall (PLAN.md section 4): pin every version and never upgrade during the thesis. The default picker may
legitimately send most requests to one pod at low load, so gateway-check sends enough parallel requests for both
pods to get some. Install and readiness timeouts are named constants in the scripts (CLAUDE.md). No logic beyond
configuration, so no unit tests.

Done when (I run this myself):
make down && make up   -> exit 0
kubectl get pods -A    -> agentgateway (agentgateway-system), inference-gateway and vllm-pool-epp (default) Running
                          next to both vllm pods
make gateway-check     -> one line per vllm pod with a count > 0; one JSON access-log line with
                          "run-id":"p12-check", "step":"1" and an endpoint; "vllm-pool-epp logged N choices for
                          21 requests" with N >= 21; "gateway-check: OK"
kubectl top pods -A    -> RAM of agentgateway, inference-gateway and vllm-pool-epp (into experiments/log.md)
