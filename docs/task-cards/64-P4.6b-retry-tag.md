# P4.6b: A step sent again shows it: "retry N" after its vLLM pod died, "resumed" after the agent's

Added 2026-11-21. PLAN.md's row P4.6, split 2026-11-20 (card 62): P4.6b is the "retry 1" tag card 60 moved here
(docs/design-system/components/PodFailureScreen: the retried step has a `failed` border and a `retry 1` tag). Also P4.4b's
live check (card 63): this card's real run with a kill, logged whichever way the kill lands.

Read before planning (Claude, 2026-11-21):
- `agent/agent_runtime/loop.py` `_send` sends a step again through `send_with_retries` and keeps only the attempt that got
  the reply: its `CallRecord` (`store.py`) has no sign of the retry; the "llm call retried" log line is the only record.
- A runtime that starts resumes a run Redis holds as running (P4.4): `run_task(saved=...)` sends the step it was on again
  with its x-step, logged "run resumed"; its record has no sign of it either.
- `loadgen/load_generator/record.py` `trace_lines` spreads each call record into a trace line, and `schemas/trace.v1.json`
  has `additionalProperties: false`: a new record field reaches trace.v1. The replayer builds its own lines field by
  field (`replay.py` ~line 308), so its output does not change.
- The UI's `retried` state (failed border, an "error" tag) is today a tool error sent back to the model
  (`ui/src/app/runs/run-view.ts` `landedCard`); the Tag card orders pod, cache, latency, then any event.
- The agent cannot name the pod a lost attempt went to: it got no reply, so no `system_fingerprint`.

Decisions (asked 2026-11-21; the user's choice in each):
1. trace.v1 gains the same optional fields as run-calls.v1, so a recorded trace says which calls were sent again; the
   replayer ignores them. (Offered: the recorder drops them, trace.v1 unchanged.)
2. A step a new runtime resumed is tagged too, "resumed", from its own field. (Recommended and not chosen: vLLM retries
   only.)
3. The card shows the tag and the failed border, no note: the lost attempt's pod is not known. (Offered: a note naming
   the previous step's pod, a guess; a note with the failure's kind, a second field.)
4. `infra/checks/failover_live.py` asserts the fields on real pods: in the vllm case the retries on the saved calls sum to
   the log's "llm call retried" lines of those runs, in the agent case each "run resumed" line has a saved call marked
   resumed. (Offered: the browser look and the replay kill only.)

Decided while planning (Claude, stated to the user):
- `retries` is left out of a record at 0 and `resumed` is left out when false, as a measurement a reply lacked is: a call
  sent once, and every record saved before this card, stays byte for byte as it was.
- `resumed` marks the first call a resumed runtime sends for the run, whether it got the reply on the first attempt or
  after retries; a run resumed twice has two. Its tag is in the retry style with the failed border, as `retry N`: both
  say the call was sent again.
- A step with a tool error and a retry shows both: the event tags first, then "error" (Interfaces below).

Built 2026-11-21 (Claude), not committed, not run on the cluster:
- `CallRecord` has `retries: int | None` and `resumed: Literal[True] | None`, both None by default, so `fields()` and
  `from_fields()` did not change and a record saved before this card reads as a call sent once. `_send` returns the
  count (attempts - 1); `run_task` marks the first record after `saved` resumed. The "llm call" log line carries both,
  as it logs `fields()`.
- The step card keeps `state` for what the model and the runtime did with the reply (the "error" tag of a tool error);
  a call sent again adds `ag-step--retried` (the failed border) through its own class binding, so a pod retry on a
  clean step is not mistaken for a tool error.
- `failover_live.py`: `RunOutcome.retries` (summed) and `.resumed` (counted) from the calls; `CaseVerdict.marks`, and a
  problem when it differs from the case's log lines; the results JSON gains `marks`.
- Two existing tests changed, with the user's yes (2026-11-21), data only, no assertion loosened:
  `test_a_case_passes_with_its_signal_and_no_problem` gets `outcome(retries=1)` (decision 4 makes a retry line with
  no retried call a failure), and run-calls.spec.ts's `Required<RunCall>` fixture gets `retries: 1, resumed: true`
  (the D12 contract test needs every schema field there). `test_failover_live.py`'s `outcome()` helper gained the two
  fields at 0 as data.
- `experiments/failover-live-p4-6b.yaml` (new): `failover-live.yaml`'s settings under a name of its own, since the
  check refuses a file whose results exist and P4.4's are committed (hash 1f5b56754c1d).
- make test exit 0 (2726 + 22 py, 254 ui, Go), make lint exit 0. Hand mutants: 12/12 Python (loop, schemas,
  failover_live), 6/6 UI killed.

Green 2026-11-21 on the user's real run (experiments/log.md): failover-live-p4-6b passed both cases with the log and the
