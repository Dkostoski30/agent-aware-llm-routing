# P1.4b: Live step cards over SSE

Goal:
The agent streams a run's steps over SSE (D6) and the UI's run view shows each step card as it lands, then the
answer.

Depends on:
P1.4a

Files allowed:
agent/ (SSE endpoint, step events, tests), ui/ (run route and its components), docs/task-cards/18-P1.4b-live-steps.md

Interfaces / outputs:
- GET /runs/{run_id}/events: text/event-stream. It first replays the run's steps saved in Redis, then sends each new
  step as it happens, then one final event with the status and the answer, then closes. A client that reconnects
  mid-run gets every step again. How new steps reach the endpoint (an in-process queue or a Redis stream) is
  settled in plan mode; either way Redis stays the source of the replay.
- Step event fields use the names of schemas/trace.v1.json and schemas/headers.v1.json (run_id, step,
  expected_steps, ...) plus the tool, its arguments, its result and invalid-call retries. Whether the event needs its
  own schema in schemas/ is decided in plan mode (D12).
- UI components ported from docs/design-system/components: RunHeader, StepCard, Status, Answer. The step line reads
  "Step 3 · 5 expected", never "3 of 5" (README: Content). Pod and cache badges come in P2.6.
- The UI uses the browser's EventSource; no new dependency.

Notes:
Tests first: agent side, the event order (replayed steps, live steps, final event) and the replay after a reconnect,
with the mocked LLM from P1.3a; UI side, cards render in arrival order and the answer slot fills on the final event.
