# P5.4: Demo rehearsal, both demos twice in a row in a driven browser

Planned 2026-11-27, on branch `feature/phase-5`, after P5.3b (card 79).

Goal:
A runbook for the two demos, the practical one (chat on the demo profile) and the infrastructure one (Start and Kill on
real), and a rehearsal that runs each twice in a row without a person touching it (PLAN.md P5.4). The rehearsal also
decides Phase 6's UI polish row: "done when the P5.4 rehearsal shows no raw errors or stuck spinners".

Depends on:
P4.6a-c (the panel's Start and Kill, the runner, the kill guard), P4.7 (the task suite's questions and scoring, the
chat path), P4.8 (step 1's pick, chat history), P4.13d (the GPU blocker check), P5.0 (the source stamp).

Decided (the user, 2026-11-27):
1. **A browser does the presenter's part**: Playwright drives the UI that `make ui` serves; if it turned out to block,
   the user would screen-record the parts by hand instead. Offered: a script on the app's API with the user watching;
   the user clicking with a runbook.
2. **Python `playwright` 1.65.1** in the root dev group (uv, locked), its Chromium installed by `make demo-browser`.
   Offered: `@playwright/test` in `ui/`; no dependency.
3. **The script assumes the cluster is up**: one command per part, the user runs `make down` / `make up` between them.
   Offered: a full cycle with the switches in the script; each part twice on its profile.
4. **One message per scenario and two extras**: a csv question with a follow-up in the same chat (history, D13), a
   contracts and a support question from P4.7's suite (csv not `two-step`, which the 1.7B gets wrong), and an
   out-of-scope message. Offered: one per scenario only; the whole suite.
5. **Steady and one Kill, as built**: Start `steady` (20 tasks), Kill the pod offered first after a fixed delay, the
   force delete of P4.6a (not P5.3b's SIGKILL, which lives in `failover.py` only), so a cut call and its `retry 1` may
   not show. Offered: two kills as P4.6a; a SIGKILL in the runner; `burst`.
6. **A raw error or stuck spinner fails the round.** Offered: report them and judge only what the demo does.
7. **Headless with a video**, `HEADED=1` for a window. Offered: always headed.
8. **One command per part with two rounds** from the file, each a new browser session and user; before the
   infrastructure part's second round it waits until both pods are Ready again. Green when all four rounds pass.
   Offered: one round per command, run twice.

The plan as approved ("go", 2026-11-27): as below, with the videos left out of git and the screenshots and JSON
committed.

Claude's choices:
- **Elements by role, label and text** (`Register`, `New chat`, the `Task` box, `Attach`'s file input, `Send`, the
  `steady` radio, `Start N tasks`, the `Pod to kill` select, `Kill pod`), so `ui/` does not change (system code frozen
  at gate-4). The spinner is the horse at `data-state="working"`, the answer `.ag-answer p`, a failure notice
  `.ag-notice--fail`.
- **A raw error** is a visible line any of `raw_errors`' 21 patterns matches (a stack trace, an exception's name, raw
  JSON, `undefined`, `NaN`, `null`, an HTTP status, `EngineCore`, and the UI's own failure captions: did not answer,
  could not be read, did not start, is not running, refused, nowhere to go, calls lost, Replay failed, The run failed),
  or a visible `role=alert` or failure notice, at any poll while the round waits. Each pattern has a text it catches
  and none catches 28 texts of a demo that goes right (tests). Console errors, failed requests and 5xx replies, which
  the audience does not see, go in `round.json` as `unseen` without failing it.
- **A stuck spinner** is a working horse still shown `settle_seconds` (15 s, three of the panel's 5 s reads) after a
  step ended: an answer shown, the replay's end.
- **A turn passes** when step 1 picked the chat's scenario, the run ended done, `go_no_go.is_correct` scores it right
  (the out-of-scope reply is the profile's `agent.out_of_scope_reply` word for word, with no tool call), and the page
  shows the run's answer, whitespace aside. The run is read from `/api/runs/{id}` through the page's own session.
- **An infrastructure round passes** when every vLLM pod was Ready before it (within `ready_timeout_seconds`), Start
  began a new replay (its `started_at` changed), Kill was pressed `kill_after_seconds` after Start, the replay ended
  `done` with the pattern's runs all finished and 0 calls lost, the kill of the pressed pod was taken, and a
  replacement was Ready within `ready_timeout_seconds` of the kill.
- **Timeouts:** an answer within the agent's own bound (`max_steps` x `llm_timeout_seconds`, as the task suite), the
  replay within 1200 s (twice P4.6a's 9.6 min), the replacement within 510 s (twice a compiled pod's 254 s without the
  compile cache).
- **Before a round** it refuses, naming the command to run, when the agent serves another model, a GPU blocker runs,
  `make ui` serves another profile or does not answer, no app backend answers through it, or (infrastructure) the demo
  runner does not answer. The GPU blocker check moved from the experiment's method to a module-level function in
  `load_generator/experiment.py`, unchanged, so both use it.
