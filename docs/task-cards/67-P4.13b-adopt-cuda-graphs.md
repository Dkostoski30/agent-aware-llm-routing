## Decided during the runs (the user, 2026-11-22)

- `pod.cpu_request: 374m`, by the card's rule: the median of 31 `kubectl top` samples between the first call and the
  last reply. On compiled pods the CPU follows the load (idle ~142m in 10 samples, 224-1219m in the rest), so the
  median no longer equals a busy pod's CPU as P3.10's did. (Offered: 497m, the median of the busy samples only.)
- Demo keeps `compiled` at 8/10 in both modes, below the card's 9/10. The card's rule (a profile that misses goes back
  to eager) is not applied: every answer equals demo's last eager run (`demo-go-no-go-1f9b63bc24ca-323935f068c4.csv`,
  2026-11-01, which the user called a go at 8/10), with the same four two-step misses, so graphs changed only the
  speed. (Offered: back to eager, per the card.)
- `make calibrate` retries a failed Windows call once (`WINDOWS_TRIES` in `sim/calibrator/calibrate.py`). The first
  run (2026-11-22, overnight) measured lora 1 pod and all 48 lora 2-pod cells. Then the clock read after the last
  cell failed: powershell.exe gave "UtilAcceptVsock: accept4 failed 110", as on P4.13's second try. That file stayed
  `.partial`, and the rerun measures it again. Tests: `sim/tests/test_calibrate.py`, a call that fails once is made
  again, and one that fails twice stops the run. (Offered: rerunning unchanged; a separate task first.)
- The retry did not save the second rerun's last file. All 8 lora cold starts were measured, then both tries of the
  clock read failed with the same error. Every failed read came with 2 pods running, and the WSL VM had 0 of 9 GB
  available, with 1 GB in swap. That powershell.exe then takes too long to start is a guess, not proven. Since then, a
  failed read after a file's last row keeps the file: the meta has `"drift": null` and `drift_error`, and the log says
  `calibrate: no drift for <file>`. A failed read before the first row still stops the run. Tests:
  `sim/tests/test_calibrate.py`, one for each case. (Offered: retries with pauses; no clock read at all.)
- The first rerun stopped at the first both-pods cold start: both pods took ~35 s to the first token for all 10 warm-up
  calls (`warmup.max_calls`). A check afterwards (both pods restarted together, with everything else on the laptop
  closed) answered in ~1 s, and the second rerun's 3 both-pods starts warmed in 2 calls. Not changed.
- The compile cache (the user, 2026-11-22, folded into this task; offered: a separate task after this one, or not
  now). Without one, every compiled pod compiled again: lora pods started alone took 244-261 s to Ready (median 254)
  against eager's 126. vLLM keeps torch.compile's output under `VLLM_CACHE_ROOT` (66 MB, one subfolder per
  configuration hash), and nothing mounted it.
  - `model.compile_cache: true` in real, real-plain and demo. The chart refuses a missing key or a non-bool. On, it
    sets `VLLM_CACHE_ROOT=/vllm-cache` and mounts the hostPath `compileCacheHostPath` there. Off, the pod is as
    before. `make vllm-deploy` makes `~/.cache/thesis/vllm-compile` and passes it. The pods write into it as root, and
    `make down` keeps it.
  - vLLM's startup plan, which would also save a free-memory baseline there, is off by default
    (`VLLM_ENABLE_STARTUP_PLAN`) and stays off.
  - Tests: `infra/checks/test_compile_cache_chart.py`. With the user's yes (rule 4), the fixtures `chart_values`
    (`infra/checks/test_drain_chart.py`) and `real_pod_values` (`loadgen/tests/test_autoscale.py`) got the host path;
    no assertion changed.
  - Both cold-start files measured without the cache are kept in `experiments/results/p4-13b-no-cache/`. The cold
    starts are then measured again with it, and `startup_duration` comes from those. The cell tables were measured
    without it; a cache changes only a pod's start.
- Validation (the user, 2026-11-23): red at 2 pods, kept as the result. At 1 pod call duration p50 was within 15%,
  run completion and TTFT p50 missed (19.8%, 16.9%). At 2 pods both compiled real pods, busy at once, generated about
