# P4.8: routing step and chat history in a token budget

Added 2026-11-23 as one card (the user's choice; offered: split into routing / re-record / history). Later the same
day the user moved the retraining and the re-recording to the end of Phase 4, so the training runs overnight: they
are P4.8b (card 70), after P4.7 and before Gate 4. This card is the code, and the live checks that need no new adapter.

Goal:
Step 1 of every agent run picks its scenario. Later steps see only that scenario's tools, and an out-of-scope message
gets a fixed reply with no tool call (D13). A chat message's run sees the chat's earlier turns (user messages and
final answers), cut to a token budget counted with vLLM's `/tokenize`. Only a drop moves the cut, so the prompt prefix
stays the same from turn to turn. The training-data generator writes routing examples, ready for P4.8b's retrain.

Proposed while planning (Claude; the plan's approval approves these):
- **How step 1 asks.** Step 1 is one call with no tool list. The prompt is the system prompt, the history and the task,
  then a routing instruction (`agent.scenario_prompt`) as a last user message. The call sets vLLM's structured outputs
  `choice` to the list. The reply can only be a scenario, so step 1 has no invalid calls in either D10 mode. A reply
  outside the list (the simulator ignores structured outputs) is an invalid call: the run asks again and counts it
  toward `agent.max_invalid_calls`. First check: one real-pod call that v0.31.0 accepts `structured_outputs.choice`
  with the LoRA adapter.
- **What later steps see.** The scenario's reply is saved as step 1's assistant message, so the step view (and the UI)
  shows the pick as step 1. The routing instruction isn't saved. Steps 2..n leave the pick out of their prompt, so they
  read system prompt, tools, history, task, as today's step 1 does. Resume (P4.4) applies the same rule.
- **The shared prefix.** The system prompt is the same text on every step. Qwen3's template puts the tool list right
  after it, so steps 1..n share everything up to the tool list. Across turns, a turn's prompt starts with the previous
  turn's history and task, until a drop.
- **Expected steps.** After the pick, `x-expected-steps` and the run's saved `expected_steps` become
  `agent.expected_steps_by_type[scenario]`, and the tracker hears the change (`RunTracker`, already built for this).
  out_of_scope ends the run at step 1.
- **The fixed reply** moves from finetune-data.yaml's `off_topic_reply` to `agent.out_of_scope_reply` in every profile,
  where the runtime and the generator both read it.
- **History in the run request.** A new optional field `history` in run-request.v1, a list of `{question, answer}`
  turns. It is optional, so the schema stays v1, as P4.6b's fields did. The app sends the chat's
  earlier turns that ended done, as user and answer pairs, oldest first. A turn without an answer is left out.
- **Counting.** Each history message is counted once per run with `/tokenize` on the pods' Service. The address goes in
  the agent manifest's environment, beside `GATEWAY_URL`. The budget compares the sum of the kept messages' counts.
  Qwen3's message boundaries are special tokens, so each message's count adds up the same as the whole. On the
  simulator `/tokenize` counts words, a stated limit.
- **The budget.** `agent.history_budget_tokens` = `model.max_model_len` minus the longest run in today's demo trace
  (its largest prompt plus its reply), rounded down, so a run never overflows because of its history. The value and
  the arithmetic go in the config comment. The routing step's prompt is the system prompt, history and task without the
  tools, shorter than any later step's, so the routing step doesn't raise that maximum. P4.8b checks the budget against
  the re-recorded trace.
- **P4.10's one-call lag ends.** With a tracker, each call's prompt (messages and tools) is counted with `/tokenize`
  before it is sent, so `thesis_context_tokens` no longer trails a call. A failed `/tokenize` is retried like a call
  (P4.4); if it still fails, the run fails like a call with no reply.
- **No feature flag.** Since the adapter is retrained with the step, no profile runs without it.
- **Training data.** Every trajectory starts with its routing example. Off-topic questions become out_of_scope picks,
  ending at step 1. A share of the examples (`history_share` in finetune-data.yaml) carry earlier turns drawn from the
  same split, so the adapter has seen prompts with history. The held-out set and both go/no-go files score the routing
  too: a wrong pick shows up as a wrong answer.

Decided while coding (Claude, 2026-11-23; told to the user):
- **A pick outside the list fails the run at once,** with `step 1 picked '<reply>', not one of <list>`. The plan above
  said invalid call and ask again. Only a server that ignores structured outputs (the simulator) can send one, and it
  would send random text again until `agent.max_invalid_calls`. Fail-fast saves those calls and keeps the pick's
  history clean. The user can still ask for the retry.
- **History items are `{question, answer}` pairs,** not `{role, content}` messages, so the order can't be wrong and
  the runtime has nothing to check.
- **The history share is training-only** (`history.share`, `history.turns` in finetune-data.yaml). The held-out set
  stays single-turn, so `make heldout BASELINE=` still pairs P4.8b's run with P2.1b's question by question.
- **A tracked run always has a counter** (`loop.Tracking`): the prompt is counted before each attempt, and a count
  that fails is retried with the call (P4.4's rule) and counted in the call's `retries`. The count from the reply's
  usage is gone, so P4.10's one-call lag is gone.
- **The app finishes ended rows before it builds the history,** so an answer the chat hasn't shown yet is in the
  next turn's history. The rows are read before POST /runs and written after it, so no write lock is held while it
  waits (chats.py's rule).
- **The step view skips the chat history** (bug found in the user's chat check, 2026-11-23): the saved messages start
  with the history, whose answers showed as steps, with each later question as a step's error and the badges on the
  wrong cards. `RunRecord.history_messages` (0 for a record saved before P4.8) tells `steps_view` how many to skip.
- **`go_no_go.served_mode` reads a run that ended at step 1 as no mode:** only an out_of_scope pick ends there,
  and in either mode.
- **Tests updated as the user chose (2026-11-23):** the scripted LLMs in `test_agent_loop.py` and `test_app.py` answer
  step 1 with the test's scenario and keep those requests in `picks`. Step numbers, saved messages and call records
  moved up by one. Retry failures are indexed over every request, the pick included, so each test still breaks the
  call it broke before. P4.10's tracker tests now check the count before sending. The loop tests' `MAX_STEPS` went
  from 4 to 5, since the repeated-call test needs five calls. `go_no_go`'s `run()` body starts with a pick.
