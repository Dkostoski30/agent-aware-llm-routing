# P2.3: Replayer: arrival patterns, tool-time gaps, fan-out, fixed seed

Decided 2026-11-02 with the user, before the code; the card below is updated to match:
- Arrivals are Poisson around the rate, so the seed gives the start times as well as the run order and "fixed rate" means
  the mean. Burst is that base rate plus n runs exactly every t seconds. The first run starts at once.
- replay.shared_prefix_tokens has two levels, since P2.2b's trace shows one number can't hold it: runs of one type share
  csv 752, contracts 736, support 800, arithmetic 336 tokens, runs of different types 192-256 (all_types was later set to 0,
  see below). A task type not listed is refused, so P2.4 adds its types with measured values instead of getting a silent
  default.
- A call with no full reply (HTTP error, timeout, cut-off stream, no usage) ends its run and the others go on, since a
  replay runs under overload on purpose and P3.4 and P4.4 count completed runs. Its line holds the planned tokens and no
  duration_ms, so trace.v1 is unchanged. The output is still written, the failures are listed, make replay exits 1.
- fan_out belongs to a pattern instead of one global replay.fan_out, so a pattern fully describes a workload and the
  output's name shows it. A third pattern, steady-fan-out, gives the done-when a live check through the gateway.

Decided 2026-11-02 with the user, after the first done-when passed but sent all 111 calls to one pod: all_types is 0, which
replaces the 192 above. P2.2b's recording split by type (csv and arithmetic on one pod, contracts and support on the other),
and llm-d-router v0.11.0 (tokenizer/estimate.go) hashes a request's tools first, then its messages. So real runs of different
types share nothing in the picker's view, while replays, which send no tools, shared their first 192 words and all went to the
pod that saw them first. Replays now share no words across types. The stated limitation: inside vLLM real runs of different
types do share 192-256 tokens, so the first call after a pod switches type has up to 256 more uncached tokens than a real
one, about 0.3 s. Sending real-shaped requests (tools, system, user) was the alternative, set aside for its cost and because
the simulator can answer a request with tools with random tool calls. Of the first replays only the fan-out stays, as
...-steady-fan-out-1-all-types-192.jsonl: a re-pasted mv overwrote the two steady ones, and experiments/log.md keeps their numbers.

Decided 2026-11-03 with the user, after the fresh-eyes review found these holes in a green done-when:
- A call's deadline is on the whole call (asyncio.timeout, agent.llm_timeout_seconds). A read timeout restarts with each
  chunk, so it never bounded a stream. The gateway's client sets no httpx timeout of its own.
- A reply whose completion_tokens differ from the plan's is a failed call: ignore_eos should give exactly max_tokens, so
  anything else was cut short or is not the trace's load. A prompt that counts differently is still recorded as the server
  reported it, and make replay-compare fails it.
- A malformed chunk fails its own call and no other (CHUNK_VALIDATOR in replay.py holds the shape of what is read), and an
  error chunk's message goes into the failure. Nulls in later chunks don't wipe a value already read. A reply that is well
  typed but breaks trace.v1, a negative count, still fails the replay after its last call: no output is written and the
  partial file stays (check_lines).
- The stream is split on newlines alone, since httpx's aiter_lines also splits on U+2028, U+2029 and U+0085.
- make replay-compare takes PATTERN= (and SEED=) and checks each replay against the plan, task_type and expected_steps
  included. Comparing two replays with each other passed on two empty files and on the same calls lost in both.
- Each run's lines go to <output>.partial as it ends, so a replay that dies keeps its finished runs. The output gets its
  real name after the last run, in the plan's order, and the partial file is then removed. A partial file left by a replay
  that stopped is refused like an existing output, since a second replay would mix with it. .gitignore is not in this
  card's files, so a leftover partial file shows up as untracked.
- A pattern that could not run is refused when the profile is read: runs or burst.runs under 1, a rate or burst interval
  of 0 or less, fan_out.share outside (0, 1], fan_out.k under 2.

Decided 2026-11-03 with the user, after the second fresh-eyes review:
- make replay-compare refuses one replay given twice (the same file, or a copy: two runs are never equal line for line) and
  a line with a duration of 0 or no TTFT. Its pass says what it checked and names what it did not: arrival times, which
  steps in the wall clock blur, prompt text, which a line does not hold, and pods.
- Counts in a profile's replay section must be whole numbers: runs, burst.runs, fan_out.k, shared_prefix_tokens. A float
  got past the checks above and failed later, mid-replay for fan_out.k.
- Kept as they are: the whole-call deadline, since a real agent's non-streaming call has the same limit, while P3.4 and P4.4
  must allow for long task types failing first under overload. compare's checks that overlap with the plan's, since the
  done-when names them. A failure's reason on stdout only, since storing it changes trace.v1: left for P3.4.
- The done-when's two steady replays are run again on the final code, since the first pair predates the deadline.

Settled in plan mode:
- Prompts are one user message of space-separated common words, one token each on the Qwen3 tokenizer (64 words checked,
  1500 random ones are 1500 tokens). llm-d-inference-sim's fallback tokenizer also counts one token per word, while it would
  count a digit string as one token, which is why not digits. The chat template adds 12 tokens, measured with /tokenize
  before planning, not assumed. All-types and per-type words never change, like a real system prompt.
- /tokenize goes to the vllm Service, not the gateway: the HTTPRoute matches only /v1, and the picker must not see the check.
- Only steps after the first fan out, since P3.6 needs a pinned pod. The k calls have identical prompts and the same x-step,
  and the next step waits for the last reply. The load of that step grows k times.
- Run IDs are <trace run id>-<start position>: the same seed gives the same IDs, so P3.3's run-to-pod map has to cope with a
  repeat. Output is refused if it exists; make replay OUT= names the second file of the done-when.
- The call timeout is agent.llm_timeout_seconds, so a replayed call fails when a real agent's would.

P2.7 check the card asks for, from llm-d-inference-sim v1.0.0's source: streaming with include_usage, cached_tokens,
ignore_eos with exactly max_tokens (pkg/dataset/dataset.go) and /tokenize with messages all exist. It has no
system_fingerprint; it names the pod in a response header x-inference-pod when POD_NAME is set (pkg/communication/http.go).

# P2.3: Replayer: arrival patterns, tool-time gaps, fan-out, fixed seed

Goal:
make replay TRACE=... PATTERN=... sends a trace's LLM calls straight to the gateway with the D1 headers, reproducing
each run's call sequence, prompt and reply lengths and tool-time gaps (D9), with runs arriving by a pattern (steady,
burst) under a fixed seed. Its own calls are recorded as trace.v1 lines with measurements, TTFT included.

Depends on:
P2.2b

Files allowed:
loadgen/ (replay module, tests), Makefile (replay), config/real.yaml, config/sim.yaml, config/demo.yaml (a replay
section), experiments/log.md, docs/task-cards/26-P2.3-replayer.md

Interfaces / outputs:
- Prompts are synthetic, since a trace holds token counts, not text: per run a seeded text, step k's prompt is the
  first prompt_tokens(k) tokens of it, so each step extends the previous one as a real agent's history does and the
  prefix cache sees a run reuse its own history. It does not see a run reuse an earlier run's repeat of the same question,
  as 22 of P2.2b's 44 later steps did, so a replay's hit rate sits below a recording's.
  Runs share a prefix of replay.shared_prefix_tokens: by_type between runs of one task
  type (the system prompt and tool definitions of the recorded runs, measured in P2.2b's traces), as real runs do, and
  all_types between any two runs (0, decided above).
  Token counts checked with vLLM's /tokenize, not a local tokenizer (no new dependency).
- Replies: max_tokens = completion_tokens with vLLM's ignore_eos, so the reply length matches the trace (supported by
  llm-d-inference-sim too: checked in plan mode for P2.7).
- Calls stream (stream: true): a replay never retries, so D6 doesn't apply, and streaming gives ttft_ms per call
  (decided 2026-11-01 with the user).
- Arrival patterns, parameters in config/ replay.patterns.<name> (D11): steady (runs start at a fixed mean rate) and
  burst (a base rate with bursts of n runs every t seconds). The run order and start times come from the seed.
- Fan-out (decided 2026-11-01 with the user, moved into the pattern 2026-11-02): replay.patterns.<name>.fan_out (share of
  later steps, k) splits a chosen step into k concurrent calls with one x-parallel-group, the workload P3.6 needs. Off
  unless a pattern sets it; a fanned-out call is marked with its parallel_group in the output trace.
- Gaps: step k+1 starts gap_before_ms after step k's reply ended (D9), not at a fixed offset from the run's start, so
  a slow pod delays the rest of the run as it would a real agent.
- Output: experiments/results/replays/<trace>-<pattern>-<seed>.jsonl, every line valid trace.v1.
- make replay-compare TRACE=... PATTERN=... A=... B=...: the done-when's check of two replays of one trace.

Notes:
Tests first, with a fake gateway and a fake clock: the same seed gives the same start times and run order, different
seeds differ; step k's prompt is a prefix of step k+1's; a gap starts at the previous reply's end; fan-out marks k
calls with one group; headers on every call match headers.v1 (contract test). Asyncio, one task per run. The
done-when compares the two replays' call sequences exactly and their measured gaps within replay.gap_tolerance_ms
(config, with a comment: event-loop and network jitter, not the agent).

make replay TRACE=<P2.2b trace> PATTERN=steady-fan-out            -> lines with a parallel_group; the gateway's access
                                                                     log shows parallel-group on those calls
