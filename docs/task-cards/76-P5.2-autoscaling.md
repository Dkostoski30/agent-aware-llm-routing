# P5.2: E2, the autoscalers on compiled real pods at 1<->2 and on simulated pods at scale

Planned 2026-11-25, on branch `feature/phase-5`, after P5.1b and P5.1c (cards 74, 75) and P4.13d's guard in
`make experiment` (its own commit).

Goal:
D5's comparison of the autoscalers on bursty load, as P5.2's row asks: completion time, throughput, time to capacity,
idle pod-minutes, interrupted runs. P4.5 ran the four autoscalers at real 1<->2 on eager pods, one seed; since P4.13b
real runs CUDA graphs, so the real square runs again on compiled pods, a seed per file, with P4.5 kept as the eager
result (the user, 2026-11-24). This card adds the simulator at scale (up to 8 pods) and a replay with a scale-down in
it, which none of P3.10's or P4.5's had.

Depends on:
P4.5 (the four autoscalers, its Williams rows), P3.10 (the sim's remaining against queue), card 73's tooling and
verdict, cards 74-75's load and seeds, P4.3 (drain), P4.13d's guard.

Decided (the user, 2026-11-25; all Claude's recommendations):
1. **Load: `burst-fan-out-heavy`,** P5.1's squares', in both squares, seeds 6, 9, 10, 13 in files a-d (card 73's rule
   checked them for this pattern). On compiled pods P4.5's `burst` likely ends before a second pod is Ready (~150 s),
   so the autoscalers would differ only in idle time. Not comparable to P4.5's eager numbers; that is stated.
2. **Real 1<->2 square:** cpu, pressure, remaining, queue, all on the default picker (D2), in P4.5's Williams rows
   (A cpu, B pressure, C queue, D remaining):

   | file | seed | runs discarded | 1st | 2nd | 3rd | 4th |
   |---|---|---|---|---|---|---|
   | p5-2-real-a | 6 | 4 | cpu | pressure | remaining | queue |
   | p5-2-real-b | 9 | 5 | pressure | queue | cpu | remaining |
   | p5-2-real-c | 10 | 3 | queue | remaining | pressure | cpu |
   | p5-2-real-d | 13 | 4 | remaining | cpu | queue | pressure |

3. **Sim square at scale** (1<->8, `config/sim.yaml`'s `max_replicas`): remaining against queue on the same load and
   seeds, the order alternating: a and c remaining first, b and d queue first. cpu and pressure do not run on the
   simulator (D5; P3.7b).
4. **Scale-down: separate files,** reported, not judged: `p5-2-scale-down-real` (the four, file a's order) and
   `p5-2-scale-down-sim` (remaining, queue), seed 6, on a new pattern `burst-gap` (below).
5. **The verdict, fixed before any run:** reference **queue**, KEDA's usual signal. Card 73's rule, gap > 0 in every
   file and the mean gap over its max-min across the files, on three numbers:
   - total run time over the kept runs: **faster** / slower (square-compare's own line);
   - when spec replicas rose: **earlier** / later;
   - idle pod-minutes: **fewer** / more, judged on the sim square only. On real 1<->2 neither autoscaler can ask for
     fewer than 2 pods (P4.5), so there only the means are printed.

   Otherwise "no difference shown". A file where a side has no rise (it never rose, or was scaled before its replay),
   or where queue idled 0, has no gap: that number gets "no verdict" and the file named. Total run time has no verdict
   when a kept run did not finish (card 73). Failed and interrupted kept runs are summed per variant, reported.
6. **Sittings:** sitting 1 is real file a alone. Rule fixed before it: if any variant's second pod takes more than 300 s
   from the rise to Ready ("capacity in" in the report; twice the 151.8 s that the one-at-a-time start measured on
   2026-11-25), or is never Ready ("capacity in -"), or a replay stalls, the rest does not run until we have looked. Reason: an autoscaler starts the second
   compiled pod while the first serves, which has never run; two pods started together froze in CUDA graph capture
   (P5.1b's file b), and a frozen new pod has no calls, so the stall check would not see it. Then one block: real
   b-d, the real scale-down, `make up PROFILE=sim`, the sim square, the sim scale-down.

Claude's choices:
- **`burst-gap`**, in every profile: 22 runs at 0.001 per second, bursts of 10 every 720 s, burst-fan-out-heavy's
  fan-out. At seed 6 that is one run at 0 s, the first burst at 720 s, one run at 1,049 s, the second burst at 1,440 s,
  and nothing after: 391 s with no arrival before the second burst, which holds the 300 s scale-down window and a 15 s
  HPA sync. A new run is what keeps a second pod: one run of 12 expected steps at its start is 12 of remaining work
  against a target of 10, past the HPA's 10% tolerance, and restarts the window. So the base rate is low and the
  bursts far apart. Searched at seed 6 only (0.001-0.0025 per second, 600-720 s): at 0.0025 and 660 s the quiet is 348 s,
  33 s of margin; at 720 s and 0.001, 76 s. A replay takes about 28 min.
- **`make autoscale-square`**, a new module `loadgen/load_generator/autoscale_square.py`: square-compare's report and
  refusals (one replay but for the seed, a seed per file, the same variants and runs, the same system hash), then per
  file each autoscaled variant's numbers from its `.meta.json` (crossings, rise, Ready, time to capacity, first
  scale-down, finished, failed and interrupted kept runs, p50, makespan, runs per minute, idle pod-minutes, KEDA
  restarts), then the verdicts of decision 5. A series is an autoscale one when its file has an `autoscale:` section
  (`idle_judged`); `make experiment-series` then ends with this report instead of square-compare's. Writes
  `<series>-autoscale.csv` and `<series>-square.csv`. `make autoscale-compare` (P4.5) stays as it is for its results.
- A gap is relative, as card 73's: (queue's number - the variant's) / queue's, so files of different seeds compare.
