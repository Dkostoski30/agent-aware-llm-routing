# P4.6c: Kill refuses the last Ready vLLM pod and says it is killing

Added 2026-11-21. Follow-up to P4.6a (card 62), from P4.6b's real run (card 64, `experiments/log.md` P4.6b entry): a
Kill press showed nothing for ~1.5 s (POST /demo/kill took 1655 and 1239 ms: the runner lists the pods, then deletes,
both with kubectl), then the select moved to the pod that was left and Kill was enabled again. The user pressed twice:
`qtx5q` was killed 2 s after `9mclc`, the chat run's step got 503 on all 3 attempts and the run failed (P4.4's rule:
replacements take 2-3 min).

Read in the code before planning (Claude, 2026-11-21):
- `loadgen/load_generator/demo_runner.py` `Runner.kill` checks only that the pod is one of the vLLM Deployment's.
- A delete with `--grace-period=0 --force` removes the pod object at once, so 2 s later kubectl lists the other pod and
  a replacement that is not Ready. The runner reads the cluster when pressed; the UI's pod list comes from the cluster
  panel's poll and can be one poll behind.
- `ui/src/app/cluster/demo-controls.ts` already disables Kill while `pressing()`, but the button looks the same.
- The runner's refusals (409 `Busy`, 404 `NoSuchPod`) reach the caption through the app backend unchanged
  (`app/app_backend/demo.py` `RunnerClient.press`), so a new refusal needs no change there or in `schemas/demo.v1.json`.

Decisions (the user, 2026-11-21):
1. The runner refuses a kill when no other vLLM pod is Ready, with a 409 the caption shows; while a press is in flight
   the Kill button reads `Killing <pod>…`. (Offered: the runner refusal only; a UI-only guard, which the poll's lag
   can let through; no fix, a stated limit.)
2. Done when the tests hold it; no live check of its own. (Offered: a short real check pressing Kill twice.)

Decided while planning (Claude, stated to the user):
- One kubectl call lists each vLLM pod's name, its Ready condition and its deletion timestamp. Another pod counts only
  when its Ready condition is `True` and it has no deletion timestamp: a pod that is draining or terminating is leaving
  (as the UI already leaves it off the select), so it is not where the runs go.
- The chosen pod's own readiness is not judged: a starting or unready pod may be killed while another serves.
- The refusal is a new exception `LastReadyPod`, answered 409 like `Busy`; the kill is not recorded and nothing is
  deleted.
- The one-pod chat demo is not touched: `app.demo_controls` is off in `demo` and `sim`.
- No PLAN row of its own: a "P4.6c green" sentence on P4.6's row.

Files: `loadgen/load_generator/demo_runner.py`, `loadgen/tests/test_demo_runner.py`,
`ui/src/app/cluster/demo-controls.ts`, `ui/src/app/cluster/demo-controls.spec.ts`, this card, `experiments/log.md`,
`PLAN.md`.
