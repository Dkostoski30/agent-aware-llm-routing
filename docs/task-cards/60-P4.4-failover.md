# P4.4: A pod killed mid-run does not end the run

Added 2026-11-19. PLAN.md's row: "Failover: pod killed mid-run, runtime retries, run continues from Redis history"; done
when "Replay with a pod kill: completion rate measured and logged". Decided by the user while planning (2026-11-19):
the answers below.

Read in the code before planning (Claude, 2026-11-19):
- The agent runtime ends a run at its first failed call (`agent_runtime/loop.py`, any httpx.HTTPError or
  LLMResponseError -> run failed). Nothing retries. Its calls are non-streaming so one can be sent again (D6), and the
  history is saved to Redis after every step (card 12: "so P4.4 can continue a run on another pod from it"), files
  included (card 14).
- The replayer never retries (card 26) and does not go through the runtime, so a replay shows a retry only if it
  applies the runtime's rule itself.
- Since P4.3 a plain `kubectl delete pod` drains the pod, so it is no failure. `kubectl delete pod --grace-period=0
  --force` is: as read so far, the kubelet then gives the pod its minimum grace (~2 s) before SIGKILL, preStop
  included, for vLLM and the simulator alike. To be checked in the Kubernetes source while building.
- The run's pin names the dead pod; the picker drops it once Kubernetes deletes it and remaps the run (P3.4).
- If the agent runtime's pod dies, its runs stay `running` in Redis until the TTL and nothing resumes them (card 18's
  known limit). The browser's EventSource reconnects and the runtime replays a run's events from the start
  (`app_backend/chats.py`), so the chat side copes with a restart. Redis does not hold a run's seed, and the store has
  no way to read a run's files back or to list running runs.
- Findings that land here: P2.6, the step view numbers steps by assistant messages, so a retry keeps its x-step;
  P3.11, gateway 500s while the picker restarts, which a retry on 5xx also saves; P3.4's second review, the delete's
  error paths can lose the picker log.

Decisions (asked 2026-11-19; the user's choice first):
1. Which failure. Both: a vLLM (or simulated) pod killed, the runtime retries the call; and the agent runtime's pod
   killed, the new runtime resumes the runs it left from Redis. (Offered: vLLM only, agent death a stated limit.)
2. Where the retry lives. One retry rule in agent_runtime that the replayer imports, as it does the run tracker (D2),
   so a replay can measure completion at scale. (Offered: runtime only, measured on live runs.)
3. What is retried. Transport errors and 5xx answers; not the deadline (overload, not a dead pod), not 4xx, not a
   body that is not a chat completion, not finish_reason length. Same x-step, same history. agent.llm_retries 2,
   agent.llm_retry_backoff_seconds 5. (Offered: the deadline too.)
4. Where the retry is recorded. Logs (runtime) and the replay's printed lines; no schema change. The UI's "retry 1"
   tag (PodFailureScreen) goes with P4.6. (Offered: an optional field in run-calls.v1 and trace.v1 now.)
   Changed while writing this card (Claude): the question said the replay writes a failed attempt as its own trace
   line. Not done: `failed_calls`, `make replay`'s exit code and the compare scripts read every line without
   duration_ms as a failed call, so a call saved by its retry would count as failed. A trace line stays one per call,
   its last attempt; each retry is a printed line, which the replay's kept .log holds (P3.4).
5. Orphaned runs. infra/manifests/agent.yaml gets `strategy: Recreate`, so at most one runtime runs at a time and every
   run still `running` in Redis when a runtime starts was left by a dead one. A second replica would need a lease
   (stated limit; D7 already scales only vLLM). (Offered: a per-run lease with a heartbeat.)
6. Live check. On the real profile, live agent runs, both kills (the agent kill cannot run on sim: the simulator's
   replies are not valid tool calls; nor in a replay, which skips the runtime). (Offered: agent kill only.)

7. Replays retry by default: replay.retry true in every profile, so a replay fails a call when the agent it replays
   would; failover.yaml's retry-off variant turns it off for the control. Results before P4.4 were taken without
   retry, which the log says. (Offered: off by default, only failover.yaml on.)
8. One task, one commit (offered: a split into the retry and the resume). The card keeps the two parts apart for
   reading; the done-when runs both checks.

# P4.4, part a: retry a call whose pod died

Goal:
A call that fails because its pod died is sent again, same step and history, and lands on another pod; a sim replay
with a pod killed measures how many runs complete with and without the retry.

Depends on:
P4.3 (committed edaff65)

Files allowed:
agent/agent_runtime/retry.py (new), agent/tests/test_retry.py (new), agent/agent_runtime/loop.py,
agent/tests/test_agent_loop.py, agent/agent_runtime/config.py, agent/tests/test_agent_config.py,
config/real.yaml, config/real-plain.yaml, config/demo.yaml, config/sim.yaml,
loadgen/load_generator/replay.py, loadgen/tests/test_replay.py,
loadgen/load_generator/failover.py (new), loadgen/tests/test_failover.py (new), experiments/failover.yaml (new),
Makefile (failover-check), experiments/log.md, PLAN.md (P4.4 row), docs/task-cards/60-P4.4-failover.md

Interfaces / outputs:
- config, every profile:
  agent.llm_retries: 2. Retries after the first attempt. One for the dead pod, one for a retry the picker sent there
  before it learned the pod left; a first guess.
  agent.llm_retry_backoff_seconds: 5. The wait before each retry: P3.4's settle, the picker's informer dropping the pod.
  replay.retry: true (decision 7). The replayer retries by agent.llm_retries and the backoff when true.
- agent_runtime/retry.py: retryable(error) -> bool (httpx.TransportError, or HTTPStatusError with a 5xx status; not
  a timeout, not 4xx, not LLMResponseError); send_with_retries(send, retries, backoff, sleep, on_retry) awaits send()
  and retries a retryable failure up to retries times, each after backoff, calling on_retry(attempt, error) first;
  the last failure is raised. Each attempt has its own agent.llm_timeout_seconds.
- loop.py: each call goes through send_with_retries; a retry is a JSON log line "llm call retried" with run-id, step,
  attempt, reason. The x-step, the tracker, the step count and the history do not change. A call that fails after
  its last retry fails the run as today, its error naming the attempts.
- replay.py: with replay.retry, _call goes through send_with_retries; a retry prints
  "replay: <run> step <n>: retry <k>: <reason>". The trace line is the last attempt's (decision 4).
- make failover-check EXPERIMENT=experiments/failover.yaml, loadgen/load_generator/failover.py: per variant, the
  file's routing (P3.4's set_routing) and a replay in-process; at kill_after_seconds the Ready pod with the most live
  pins in the picker's log (choose_pod) is force-deleted (grace 0); the replacement is waited for. P3.4's second
  review applied here: the picker's log is fetched before anything after the replay can fail, what is known is
  written on an error, the cluster's profile is checked against the file's, a dead kill thread's traceback goes to
  the kept .log, a kubectl wait error is told from its timeout. Results in experiments/results/ stamped with the
  file's hash: replay lines, printed lines, picker log, .meta.json, and a report per variant:
  - runs started, runs done, completion rate; runs failed by their deadline counted apart;
  - calls running on the killed pod at the kill: each failed, retried (to which pod, with what outcome) or answered;
  - retries in the variant, and runs failed by the kill (a failed call among those, reason not the deadline);
  - runs pinned to the killed pod and remapped (P3.4's lines); the picker's restarts (P3.11).
  Retry-on passes with at least one call running on the killed pod at the kill and no run failed by the kill; with
  none running there it is void. Retry-off is the control, counted. Exits 1 if retry-on did not pass.
- experiments/failover.yaml: profile sim, routing {plugin: true, affinity: true}, P3.9b's converted trace, burst,
  seed 6, the profile's 2 pods, kill_after_seconds 125 (P4.3's: the pods hold queues), wait_for_calls_seconds 60,
  settle_seconds 5; variants retry-off, retry-on.

Notes:
- A killed pod's stream may end as a short reply (ReplyError) rather than a transport error; the rule does not retry
  that. If the run shows it, the report names it and the rule's change is asked, not made.
- The simulator's 30 s drain does not apply: SIGKILL follows the minimum grace.
- Priority (P4.1): a retry reaches the picker later, so it gets a later arrival in its priority; not changed.
- Tests first: retryable on each error kind; send_with_retries (first try, retry then success, out of retries, backoff
  awaited, on_retry order); loop: a 503 then a reply keeps the step and the history, a timeout is not retried;
  replay: a cut call retried, its line the last attempt's; failover report from hand-written lines (completion rate,
  groups, void). Each rule line changed once to check a test fails.

Done when: with part b's.

# P4.4, part b: resume the runs of a dead agent runtime

Goal:
When the agent runtime's pod dies, the next runtime continues each run it left from its saved history in Redis; a
live check on real pods kills a vLLM pod, then the agent pod, mid-run, and every run ends done.

Depends on:
part a

Files allowed:
agent/agent_runtime/store.py, agent/tests/test_store.py, agent/agent_runtime/app.py, agent/tests/test_app.py,
agent/agent_runtime/loop.py, agent/tests/test_agent_loop.py, infra/manifests/agent.yaml (strategy Recreate),

Interfaces / outputs:
- store.py: the run's seed in its hash; a set thesis:runs:running (added in the transaction that saves a new run,
  removed in the one that saves its end); running_runs(); get_files(run_id). Under the run's TTL as today.
- loop.py: run_task takes an optional saved state (messages, step, invalid_calls, calls). It starts from it: the step
  the dead runtime was on is sent again with its x-step, the repeated-call set is rebuilt by check_call on the saved
  tool calls, the first call's gap_before_ms from the last saved call's end by the wall clock (no monotonic clock
  survives a process).
- app.py: at startup, every run in thesis:runs:running is read with its files and seed, counted in the tracker
  (expected_steps from its record) and resumed in the background; a JSON line "run resumed" with run-id and step.
- agent.yaml: strategy Recreate (decision 5).
- make failover-live EXPERIMENT=experiments/failover-live.yaml, infra/checks/failover_live.py: profile real (checked
  against the cluster). Two cases, each: the file's questions from experiments/real-go-no-go.yaml with sales.csv sent
  as runs to the agent; at kill_after_seconds case vllm force-deletes the vLLM pod with the most live pins, case
  agent force-deletes the agent pod and reaches the new one by its pod IP (go_no_go.py's reason: the Service lags
  >10 s). Each run is polled to its end. A case passes when every run ends done, no saved step before the kill
  changed, and its calls' steps are 1..n each once; it is void without a retry logged (vllm) or a run resumed (agent).
  Answers are scored and counted, not judged (P4.7 judges them).
- experiments/failover-live.yaml: questions and seeds (a first guess: the 5 questions x seed 1), kill_after_seconds.

- Demo profile has one vLLM pod: a kill there leaves nothing to fail over to until the new pod loads. P4.6's

- Tests first: store (seed, running set in and out, files back); loop resumed from a saved state (x-step of the lost

Built 2026-11-19/20 after "go" (Claude), not yet run on the cluster. Changed or added while building:
- Read in Kubernetes v1.36.5 (pod_workers.go, kuberuntime_container.go): a force delete at grace 0 gives the pod 1 s
  (the pod worker's floor) of its preStop, then SIGTERM, then SIGKILL after the 2 s minimum: ~3 s, on vLLM and the
  simulator alike. The card's "~2 s" was close; failover.py's docstring has the read.
- A run that fails after its last retry keeps today's error text (record.py's NO_REPLY and heldout.py's
  CLUSTER_FAILURES match its start); the "llm call retried" lines count the attempts, not the error.
- The replay's retry line names when the failed attempt was sent ("retry <k>, attempt sent at <ms>: <reason>"), so
  failover.py places a retried call by its first attempt, whose pod is the run's pin at the kill (a failed attempt
  names no pod).
- failover.py has its own kubectl, which keeps kubectl's message on the error, so a kill or a wait that failed is told
  from one that timed out. A kill's error and the replacement's are written in the meta, not raised; the picker's log
  is written to its file before the replacement is waited for; stderr goes to the kept .log with stdout. The meta is
  written after the last variant, so a replay that dies leaves each finished variant's lines, .log and picker log.
- Fixtures that gained a key or a command, no assertion changed: make_config in agent/tests/test_agent_loop.py and
  agent/tests/test_app.py (retry=NO_RETRY), test_replay.py's tiny profile (replay.retry, agent.llm_retries,
