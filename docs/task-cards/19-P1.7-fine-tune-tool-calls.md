# P1.7: Fine-tune the 0.6B on generated tool-call trajectories

Goal:
A LoRA adapter on Qwen3-0.6B that calls the D10 tools right more often than the model served today: chained
arithmetic (2x2x2, 7 times 8 plus 3), the CSV questions, and the two-step question (P1.6b-f: the 0.6B stops after the
first of two dependent calls). The tools are deterministic, so Python generates the training trajectories (question ->
tool calls -> real tool results -> answer): no teacher model, no hand labels.

Depends on:
gate-1 (P1.6 go, agent thesis/agent:99df636ae969). Checkpoint 1: the mentor agreed that fine-tuning fits the thesis.

Decided 2026-10-28 with the user:
- Base model: Qwen/Qwen3-0.6B in full precision with plain LoRA; no QLoRA, no bitsandbytes. The adapter is served on
  the Qwen3-0.6B-GPTQ-Int8 that the real profile already runs, and D8 stays: the demo keeps the 1.7B. The demo
  go/no-go questions run on the real profile (experiments/real-go-no-go.yaml). Moving the demo to 0.6B + adapter
  would change D8, so it is a separate question after step 3.
- Off-topic questions are trained to give the P1.6e sentence and call no tool: "I can only do arithmetic and answer
  questions about attached CSV files." The system prompt does not change.
- One step at a time, in order. Each step gets its own plan, approved before its code.

Training environment:
training/ is its own uv project (pyproject.toml, uv.lock). The root workspace lists only agent as a member, so uv
already treats training/ as a separate project (tested 2026-10-28) and uv sync at the root, the agent image and the
root venv never install torch. New dependencies, each asked for in step 1 with its exact version (the newest release
at least two weeks old, versions.md): torch, transformers, peft, accelerate (transformers' Trainer needs it), and
huggingface-hub (spike.py downloads tokenizer files with it; added 2026-10-28). Not used: trl (the Trainer plus a short
collator is enough and easier to defend), bitsandbytes (only QLoRA needs it), datasets (the JSONL is read with json).
mypy 2.4.0 and pytest 9.1.1 go in its dev group at the root's pins.
Generated data, checkpoints and adapters live in ~/.cache/thesis/finetune/, outside git. The commands below rebuild
them.

PLAN.md gets one row: P1.7 in Phase 1, with step 3's done-when. No decision D1-D14 changes.

Step 1 · Feasibility spike (max 1 hour; stop and report if it fails; no training data yet)

Files allowed:
training/pyproject.toml, training/uv.lock, training/spike.py, experiments/finetune-train.yaml (base model, revision,
LoRA shape, the lengths to measure; step 3 adds the rest), .pre-commit-config.yaml (the root mypy hook skips
training/, a second mypy hook runs in the training env), infra/local/vllm-common.sh (optional extra vLLM flags),
infra/checks/lora_check.sh, Makefile (finetune-spike, lora-check), versions.md (training packages, the Qwen/Qwen3-0.6B
revision), PLAN.md (the P1.7 row), experiments/log.md, this card

What it proves:
- One training step fits in 4 GB with the cluster down. training/spike.py downloads Qwen/Qwen3-0.6B at the pinned
  revision, loads it in bf16, adds LoRA at the largest shape step 3 would use (rank 16 on every attention and MLP
  projection), turns on gradient checkpointing, and runs 5 optimizer steps on one sample at each length. It prints
  the peak VRAM (torch's max_memory_reserved and nvidia-smi's used memory), seconds per step over steps 2-5
  (step 1 includes CUDA warmup), and saves the adapter.
- The lengths are 2048 and 4096 tokens, not the longest real prompt (changed 2026-10-28 with the user): building that
  prompt needs the agent runtime (root env) or step 2's generator. 4096 is model.max_model_len, so no prompt the
  runtime sends is longer; if it fits, no length question is left. Step 2 measures the longest real example, step 3
  sets the max length from it.
- Known risk: for a 2k-token sample, the logits over Qwen3's 151,936-token vocabulary take ~1.2 GB in fp32. If that
  doesn't fit, the loss can be computed on the reply tokens only (lm_head applied to their hidden states alone). That
  is a plan change I bring back to you, not a silent fix.
  It happened in the first run (2048 needed 5940 MiB, 4096 ran out of memory on the fp32 logits; experiments/log.md).
  Decided 2026-10-28 with the user: the logits are computed for the last spike.reply_tokens (64) tokens only
  (transformers' logits_to_keep), the loss counts those, and the spike exits 1 when torch's peak is more than the VRAM
  free before loading (under WSL, CUDA spills into shared system memory instead of failing).
- Training renders with the template vLLM serves: Qwen/Qwen3-0.6B and Qwen3-0.6B-GPTQ-Int8, at their pinned revisions,
  have the same tokenizer.json and chat_template (sha256 of each, in the log). If they differ, the GPTQ one is used.
- vLLM v0.31.0 serves the adapter on the GPTQ-Int8 model. make lora-check starts the real profile's vLLM container
  (as make vllm-run does) with --enable-lora, --lora-modules and --max-lora-rank. It sends "What is 7 times 8?" with
  the agent's calculator tool, in both D10 modes, to the base model and to the adapter, and prints the VRAM used
  with and without the adapter. Changed 2026-10-28 with the user, after the first run: the spike's adapter is trained
  on repeated text, not neutral, so it is not required to call the tool (it answered "The result is 56." in auto
  mode). Every request must be answered, and in required mode both must return a parsed calculator call, which also
  shows the hermes format; an adapter answer that differs from the base model's shows that vLLM applies it.
- The text that required mode makes the model write: read in vLLM v0.31.0's code (inside the image) what tool_choice
  "required" constrains the output to, hermes <tool_call> tags or a JSON list. Step 2's required-mode targets are that
  text.
- Whether two real pods still fit with the adapter: they need ~3.06 of the 3.22 GiB free (P0.4), which leaves ~160 MiB
  for the adapter's extra VRAM per pod.

If vLLM can't load the adapter on GPTQ-Int8, I stop, list the options with their cost and ask:
- serve the FP16 0.6B: 1.5 GB of weights, two pods don't fit, a D8 change;
- merge the adapter into the FP16 model and re-quantize to GPTQ-Int8: new tools (a GPTQ quantizer, calibration data)
  and about an hour of GPU per adapter;
- stop P1.7.
If two pods don't fit with the adapter, the options go to you as well: one pod for P1.7's runs, or a smaller
kv_cache_memory_bytes (480 MiB holds ~4400 tokens, max_model_len is 4096).

make lora-check                           -> exits 0; base and adapter answers in both modes, a parsed calculator
                                             call from both in required mode; VRAM with and without the adapter

Step 2 · Data generator, held-out set, baseline (stdlib + agent_runtime; no new dependency)

Files allowed:
experiments/finetune-data.yaml, experiments/finetune_data.py, experiments/heldout.py, experiments/go_no_go.py (two
expected kinds, an optional adapter hash in the result name), experiments/real-go-no-go.yaml,
experiments/tests/test_finetune_data.py, experiments/tests/test_heldout.py, experiments/tests/test_go_no_go.py (new
tests only; existing tests stay as they are), Makefile (finetune-data, heldout, EXPERIMENT for go-no-go),
experiments/results/ (the baseline CSVs), config/real.yaml (agent.answer_tolerance, the demo's 0.01, which the
scorer reads; added 2026-10-29 with the user), experiments/log.md, this card.
Added with the user on 2026-10-29 (the token lengths step 1 left to step 2): training/render.py,
training/tests/test_render.py, training/pyproject.toml and training/uv.lock (pytest 9.1.1 in the dev group, its
pytest settings), pyproject.toml (the root's pytest skips training/), Makefile (make test runs training/tests when
training/.venv exists), versions.md.

Interfaces / outputs:
- experiments/finetune-data.yaml (D11) holds every size and seed, each with a comment: the generator's seed; CSVs for
  training and for held-out; rows per CSV and groups per column; training examples per kind and mode; held-out
  questions per kind (14, see heldout.py below); the profile whose agent settings the trajectories use (real:
  system_prompt, result_decimals, max_result_rows, max_files); the output directory. The training size is set from
  step 1's s/step so one epoch fits in a night.
- CSVs: column names, group values and value ranges come from word lists in the generator, and none of them is a
  sales.csv name (region, product, month, units, revenue). Training and held-out use disjoint lists, so no held-out
  column or group name appears in training. Values are drawn like demo-go-no-go.yaml's: every wrong-but-plausible
  answer (another group's value, the sum over all groups) is more than agent.answer_tolerance from the right one,
  and two-step has no tie.
- Question kinds, several phrasings each: summary, group-total, group-mean, compare, two-step, chained arithmetic (2-4
  operations), off-topic. Arithmetic and off-topic runs get a CSV half the time, because the runtime offers the
  calculator next to the CSV tools (P1.6f isn't done). Held-out uses the same phrasings on unseen CSVs and numbers. The
  hand-written go/no-go questions remain the test for phrasings the generator never wrote.
- Trajectories: the generator plans each question's calls. Two-step, for example: group_by(by, rank value, sum),
  then group_by(by, value, sum), then the answer. It runs the plan through the agent's own loop:
  agent_runtime.loop.run_task with a scripted LLM, an LLMClient subclass whose chat() returns the planned reply and
  records the messages and tool definitions it got. Every prompt is then exactly what the runtime sends, every tool
  result comes from the real tool, in both D10 modes: required ends with a final_answer call, auto with a text
  answer. One training example per assistant turn: {tools, messages so far, reply}. The final answer is a sentence
  with the number as the tool result shows it.
- Held-out set: JSONL of go_no_go's Question shape (text, expected_calls, expected, wrong_if_matches) plus the file.
  The expected value comes from go_no_go.expected_value on the CSV, independent of the tools.
- go_no_go.py gets two expected kinds. arithmetic: a start number and a list of (op, number) applied left to right,
  computed with the operator module. fixed_reply: correct when the run is done, no tool ran and the answer contains
  the sentence. result_path takes an optional adapter hash; without one, the name is the same as today.
- experiments/heldout.py scores the held-out JSONL through the agent in k3s with go_no_go's run_question and
  is_correct, in each mode, switching the profile as go-no-go does. It writes one CSV row per run as the run ends and
  prints the score per kind and mode. A run cut short keeps its rows, and the next run asks only the questions with
  no row. A run whose LLM call got a 5xx (a 503 while vLLM isn't ready) or no connection stops it without a row:
  that's the cluster, not the model. Any other failed call is a wrong run, such as a 400 when the model loops past the
  4096-token context (added 2026-10-29 with the user, after Windows sleep stopped the first baseline and a re-run on a
  cluster that wasn't ready wrote over its CSV; narrowed to 5xx the same day, after heldout-compare-0322's 400). One seed per question: different questions spread the score in a way two seeds of one question
  didn't (P1.6c). 14 per kind, 98 questions (decided 2026-10-30 with the user, down from 100 per kind, 1400 runs and
  4-6 h per pass; the first baseline's 321 runs at that size are dropped): the 95% margin per mode (98 runs) is ±10
  points, so a clear overall gain shows; per kind (14 runs, ±26) the score is only a hint. 196 runs, ~40 min on two
  0.6B pods at 10-14 s per run (P1.5), once for the baseline and once for the adapter.
- experiments/real-go-no-go.yaml: demo-go-no-go.yaml's file, seeds and questions with profile real. A test checks that
  they stay equal.

Tests first:
- generator: the same seed gives byte-identical output; every kind and mode has the configured count; held-out and
  training CSVs share no column or group name and use none from sales.csv; every recorded tool result equals what
  run_tool returns for that call; every trajectory's final number is within tolerance of expected_value; no two-step
  tie; off-topic answers are the sentence with no tool call;
- scorer: both new kinds, with right and wrong runs.

Interfaces / outputs:
- experiments/finetune-train.yaml (D11): the finetune-data hash it trains on, epochs, learning rate and warmup, LoRA
  rank, alpha, dropout and target modules, max length, batch size and gradient accumulation, save and log intervals,
  checkpoints kept, the seed. Each has a comment why; first values come from step 1's VRAM and s/step.
- make finetune trains from that file. Loss only counts the reply's tokens (the prompt is masked), and the logits are
  computed for those only (logits_to_keep, step 1). The loss goes to a JSONL line per log step (tail -f to watch it).
  If the output directory has checkpoints, it resumes from the newest, so a crash or Ctrl+C costs at most one save
  interval. The output directory is named after the config's hash, so a
  changed config never resumes an old run. It refuses to start while a vLLM container or pod holds the GPU. At the end
  it saves the adapter to ~/.cache/thesis/finetune/adapters/<sha12 of adapter_model.safetensors>/ and prints the path,
  sha256, peak VRAM and total time.
- Serving: config/real.yaml gets model.lora (name, path, sha256, max_rank), with a comment. The vLLM chart renders the
  LoRA flags from it, and the agent sends the adapter's name as the model. Whether model.lora stays in real.yaml after
  step 3 is your call, since every experiment would then run on the adapter.
