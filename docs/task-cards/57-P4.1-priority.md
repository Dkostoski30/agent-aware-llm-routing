# P4.1: Runs close to finishing go first, with a bound on how long a call can be overtaken

Added 2026-11-19. The first Phase 4 row. D3: the plugin sets a per-request priority and vLLM's priority scheduling
enforces it, if it works through the gateway. If it doesn't, the fallback is PLAN.md section 4's: the runtime and the
replayer set it.

Read in source before planning (2026-11-19):
- vLLM v0.31.0 (the pinned image, `vllm/config/scheduler.py`, `vllm/v1/core/sched/request_queue.py`, `scheduler.py`):
  `--scheduling-policy priority` orders the waiting queue by `(priority, arrival_time)`, lower first. When KV blocks run
  out, the running request that is largest by the same pair is preempted. The body's `priority` (int64, default 0) is
  refused with a 400 when the server runs `fcfs` and the value isn't 0. A queued request's priority never changes.
- llm-d-router v0.11.0 (`requestcontrol/director.go`, `parsers/common.go`): the body goes to the pod unchanged unless
  `requestHandler.propagatePriority` is on. When it is on, the router writes the InferenceObjective's single priority,
  negated for vLLM, and drops the client's. PreRequest plugins get the same `InferenceRequestBody` that the director
  re-serializes afterwards. `MutatePayloadMap` changes the payload and marks it mutated, so the changed body is what
  the router hands to the gateway. Whether agentgateway v1.6.0 sends that changed body on to the pod is not in the
  source we hold, so the live check proves it.

# P4.1: priority by progress, with aging

Goal:
With routing.priority on, every call through the gateway carries a vLLM priority written by thesis-run-router: calls of
runs close to their expected steps go first, and no call is overtaken by a call that arrived more than
routing.priority_aging_seconds after it. The pods run vLLM's priority scheduling. One command shows the order live.

Depends on:
Gate 3 (P3.2's plugin and flags)

Files allowed:
gateway/runrouter/priority.go (new), gateway/runrouter/priority_test.go (new), gateway/runrouter/plugin.go,
gateway/runrouter/plugin_test.go, gateway/runrouter/flags.go,
config/real.yaml, config/real-plain.yaml, config/demo.yaml, config/sim.yaml,
infra/charts/vllm/templates/deployment.yaml, infra/local/vllm-common.sh, infra/routing-values.sh,
loadgen/load_generator/experiment.py, loadgen/tests/test_experiment.py, loadgen/tests/test_routing_values.py,

experiments/log.md, PLAN.md (P4.1 row, D3 note), docs/task-cards/57-P4.1-priority.md

Interfaces / outputs:
- config: model.scheduling_policy (priority in real, real-plain, demo; fcfs in sim, whose chart doesn't read it);
  routing.priority_aging_seconds (first guess 30: about one median real run, 27-29 s at Gate 2, so a run's first step
  can be overtaken only by calls arriving within one typical run after it; P5.1 measures it).
- The chart passes --scheduling-policy={{ model.scheduling_policy }}; vllm-common.sh passes the same, as the chart's
  comment requires.
- routing-values.sh and experiment.py refuse routing.priority true on a profile whose model.scheduling_policy isn't
  priority (vLLM would answer 400). On sim this always refuses: the simulator has no priority scheduling.
- Plugin, flag on: for EVERY request, including ones without x-run-id (a request with no priority field counts as 0,
  ahead of everything), the body's priority = now in Unix ms + round(aging_ms × (1 − progress)),
  progress = min(step / expected-steps, 1). A missing or invalid x-step or x-expected-steps counts as progress 0, the
  most slack. Flag off: body untouched. Written in PreRequest through MutatePayloadMap. propagatePriority stays off.
- The "Run call picked" line gains priority when the flag is on.
- make priority-check PROFILE=real: through the gateway, 8 fillers (x-step 1, x-expected-steps 10, a unique ~1500-token
  prompt each so the prefix cache can't share them, max_tokens 150, ignore_eos, streamed) and then, once they're
  queued, one finisher (x-step 10 of 10, same size). It records each call's send time, first byte and pod
  (system_fingerprint). Verdict: the finisher's first byte comes before every filler on its pod that hadn't started
  when it was sent. It runs once with the profile's routing plus priority on and once with priority off (the control:
  the finisher waits its turn), and puts the profile's routing back at the end.

Notes:
- D3 unchanged in substance. Its row gets a note naming the plugin as the setter and the deadline form of aging (decided
  2026-11-19).
- Aging as decided (2026-11-19): vLLM can't raise a queued call's priority, so the bound is on overtaking, not on wall-
  clock wait. Proof: a call A has slack at most aging_ms, and a call B arriving more than aging_ms later has a priority
  above A's before its own slack is added.
- With priority off, every call is 0 and vLLM's waiting queue is first come, first served as before. Preemption now
  evicts the latest arrival instead of the last scheduled call, a small change from what P2.8 calibrated. Recorded in
  the log, not rerun.
- Priority acts only on a pod's own waiting queue and its preemptions; it never moves a call between pods. It matters
  only when calls wait, which on real pods is KV admission (P3.7: 8-12 waiting per pod after bursts).
- Fallback (PLAN section 4): if the check shows agentgateway drops the changed body (the finisher's order equals the
  control's, and the picker log shows the priority written), stop and report (rule 8). Moving the field into the agent
  runtime and the replayer is a new plan.
- Tests first: the priority table (progress 0, between, 1, past expected, missing and bad headers, aging 0), the
  overtaking bound as a property over generated arrivals, PreRequest writes the field for a request without x-run-id
  and leaves the body alone with the flag off, the config refusals, and the check's verdict on hand-written timings.
