# P3.2: Plugin skeleton, flags from the profile

Decided 2026-11-09 while planning Phase 3: the plugin is a **filter**, not a scorer as PLAN.md's first wording had it. A scorer's weight can be outvoted by the queue and KV scorers, so "pinned" would only mean "usually". A filter that returns only the pinned pod is a hard rule, and returning every pod hands the choice back to the default scorers, which is what "first step picked by load + prefix" asks for. Upstream splits it the same way (`session-affinity-filter`).

`routing.plugin` is a master switch, off in every profile until Phase 4's demo needs it. With it off the picker runs the chart's `default-plugins.yaml`, so Gate 2's experiment files stay valid (their `epp_config` names that file).

Decided 2026-11-10 with the user, while planning: `make up` passes its profile to `infra/install-gateway.sh`, which applies the profile's routing as `set-routing.sh` does, so `Makefile` joins the allowed files. `set-routing.sh <profile> [file]` keeps one file argument and tells rules from Helm values by the top key: `routing:` is rules for `routing-values.sh`, anything else goes to helm, a file with both is refused.

Decided by Claude in the plan, stated to the user: all five flags are required (a missing or null one is refused, so the profile is the only source); the plugin registers as Beta, since Alpha needs `--allow-experimental-plugins`, which would also let upstream's Alpha plugins load; a variant's `values` and `routing` are exclusive, since a routing variant needs our image on `thesis-plugins.yaml` and every values file swaps one of them; routing keys are checked against the variant's profile before the cluster is touched; PreRequest logs the picked pod under `run-id` at verbosity 3, the level of upstream's "Request handled", and nothing for a call with no `x-run-id`; Go tests use the standard library only, since upstream's `test/utils` pulls in testify. `logr` and `apimachinery` moved from indirect to direct in `go.mod`, same versions, `go.sum` unchanged.

Found on the cluster (2026-11-10): two bugs in `set-routing.sh`, in lines no unit test reached (experiments/log.md). After the fresh-eyes review the user added `loadgen/tests/test_routing_values.py` to the allowed files: it runs `routing-values.sh` and `set-routing.sh` from a copy of `infra/` with fake helm, kubectl and curl. The review's silent fallbacks are refused now: a profile missing one of the six routing keys, a routing section that is not a map, and a rule on while `plugin` is off. The second review: a profile with a routing key beyond the six is refused too, and `check_routing` refuses a rule on while `plugin` is off before the cluster is touched, as it does unknown rules.

For Phase 4 (the review, 2026-11-10; the user chose a note over a fix): `set-routing.sh` lays the profile's routing under every variant, a Helm values file included. Once a profile sets `routing.plugin: true`, as the demo will, `router-upstream-values.yaml` would run upstream's image on `thesis-plugins.yaml`, which does not know `thesis-run-router`, and fail after the 300 s rollout timeout; the round-robin values would replace the config file and drop the plugin. Phase 4 decides whether a values variant skips the profile's routing. Nothing runs that way today: `routing.plugin` is false in every profile.
