# P4.12: KEDA scales real pods on context tokens

Added 2026-11-16 (Claude's proposal, planned at the user's request). First to drop if Phase 4's week runs over (PLAN.md).

The idea: the pods a pool needs = the context its active runs hold / what one pod's KV cache holds. The target is then a figure of the hardware, where `remaining_work_target: 10` is a first guess that P3.9b could not improve without tuning to the test.

The risks to know before running. This may show no gain, and then the numbers and the cause are the result (rule 8):
- Real pods only. The simulator limits by `max_num_seqs` and prices a cache hit as prefill compute (P3.7b), so it cannot show this, and there is no result past 2 pods.
- The second pod shares the one GPU: it adds a KV cache, not compute, and pods have starved each other of the GPU (P3.7c).
- Its model load takes about 2 minutes and starved k3s's datastore before; the KEDA operator lost its lease 3 times (P3.9a). A 5-run burst is past the bend before the pod is Ready.
- Like remaining work, the signal counts runs already started, so it cannot see a burst coming (P3.9b).

## Decided while planning (2026-11-20)

The user:
- The context-tokens crossing and the three first-token windows are reported for every autoscaled variant (remaining, queue,
  cpu, pressure), so P4.5 compares all four on the same numbers. So `autoscaling.pressure_target` is in sim.yaml too, read
  there only for the report; the pressure autoscaler stays refused on sim.
- The windows count kept runs only, as every other number of the report, later steps (step 2 and on) with a first token,
  each placed by when it was sent on the VM's clock (`ts_start`, the clock Prometheus stamps with); each window prints its
  call count.

Claude's choices:
- The threshold is round(`model.kv_cache_tokens` x `autoscaling.pressure_target`) tokens per pod: 4384 on real at 1.0. The
  crossing is per pod of spec replicas and past the threshold, as remaining work's and the queue's.
- The windows: before = sent before spec replicas rose; rise-to-Ready = from the rise to the first sample with that many
  Ready (as `time_to_capacity`); after = from Ready to the first scale-down, or the replay's end. With no rise, every call
  is "before" and the other two are empty.
- The autoscale CSV gains two columns: `context_tokens` (sum(thesis_context_tokens)) and `keda_restarts`
  (kube-state-metrics' restart count of the `keda-operator` container in namespace keda). The report counts the
  restarts' rise between the scale-up and Ready, and over the replay. Existing tests whose expected rows or CSV header
  list the columns gain the two (spec change, stated).
- The report's moments: context passed the threshold, spec replicas rose, the second pod Ready, the first scale-down (or
  none); then the three medians with counts and the restarts.
