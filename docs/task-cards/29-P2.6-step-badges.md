# P2.6: Per-step badges: pod, cache hit, latency

P2.6 is split in two (2026-11-04): P2.6a file attach in the composer, P2.6b the badges. P2.6c (2026-11-05, block at the
end) came out of the first free-form CSV run after attach. Decided with the user in plan mode, 2026-11-04:

Scope: badges only. The step table, the Answer/Steps tabs and the step detail sheet, which card 18b, card 15d and the
design system's StepTable and StepsTabScreen cards place in P2.6, have no task; at most Phase 6 polish if time is left.
The table's TTFT column could not be filled for agent calls anyway (D6).

Attach is pulled forward from P3.13: the card's done-when needs a CSV question, the UI sent only the task text, and the
agent offers the CSV tools only on a run with a file. Several files, .csv as csv, .txt and .md as text, sent straight to
the agent in the run request until P3.13 puts the app backend in between. The UI refuses only what it cannot turn into
a run-request file (another extension, a name with letters an ID cannot keep or with nothing to build one from, content
that is not UTF-8, a file too large to read) and renames nothing; the agent stays the one place that checks duplicate
IDs, agent.max_files and agent.max_file_bytes, and the reason it gives with its refusal reaches the composer's hint.
Decided after the review: a name with non-Latin letters is refused, since продажби-2025.csv and приходи-2025.csv would
both get the ID 2025 and fail on a duplicate the user never typed.

How the badges get their data: a new GET /runs/{id}/calls and a new schema, run-calls.v1. The card first said the step
event gains an optional call. run-events.v1 has no optional fields (every field is required, null when empty) and
test_app.py's checked() enforces that, so that design would have had to edit an assertion. Of three fixes explained to
the user (call required and null when absent, a separate request, exempting call in the test), the user chose the
separate request: run-events.v1 and its tests stay unchanged. The UI asks after each step event; every answer holds all
the calls so far, so a newer step replaces a request still waiting and the next answer makes up for a failed one. A card
can show for a moment before its badges. A failed request leaves a line under the cards until an answer arrives; there
are no retries, so after the last step it stays until a reload. The endpoint returns whole records, as saved, so there
is no second shape and they equal Redis. It also gives P3.13's history a way to get badges. Added to D12's list.

Store: a new RunStore.get_calls; get stays as it is, so GET /runs and P4.4 don't read calls they don't need. The existing
tests change only in setup, with no assertion changes. MemoryStore gains get_calls and FakeRedis gains get and values in
a separate "Tests:" commit (PLAN.md rule 5). SCHEMA_NAMES gains run-calls.v1 and run-screen.spec provides a fake RunCalls
in P2.6b's own commit, since both need its new files.

Cache badge: "99% cached", the exact counts on hover ("768 of 779 prompt tokens cached", the wording of the design's step
sheet). Teal when cached_tokens > 0, an outline at exactly 0, no threshold. The shared system prompt gives cached tokens
on any warm pod (P2.2a), so the color says something was cached and the percent says how much; a moved step shows teal
with a low percent. Changed by the user after seeing the first real run: "768/779 · 99%" pushed the duration onto its own
line and read as unlabeled numbers. Rounded down, so 100% means every token was cached. Numbers no reply should hold (0
prompt tokens, more cached than the prompt, a negative count) and an empty pod name show no badge; the agent only checks
their types (card 24), and P2.7's simulator is unverified. These differences from the design system are recorded in D14. Pod badge: the name without its ReplicaSet hash (vllm-6bq8s), the full name on hover; a name
not shaped like a Deployment's pod stays as it is. A field the call record lacks hides only its own badge (P2.2a's rule:
a missing measurement never reads as 0).

P2.6c, decided with the user 2026-11-05, after run-e3ed93177366 ("who left highest review?" on a reviews CSV). The model
called compare with column names as groups. The tool's error listed 20 of 71 IDs of 68 random characters, ~1,000 tokens
(prompt 801 -> 1,897). The model then gave the first ID as the answer and the run read Finished, the only sign being a
missing footer. The right answer has no single name: 61 authors gave 5 stars.

The limit is 560 characters, not the 1,600 first proposed, since 20 such IDs are ~1,400 characters and 1,600 would not have
touched this run. It counts group names only, in group_by's rows and compare's error. group_by had the same gap: a file's
free-text column would have put 20 long texts in the context. If not even the first group fits, the result is a tool error
rather than empty rows, which would read as a success. The flag is shown, the run is not rejected: rejecting it changes
D10's loop and the traffic, and would need the go/no-go again. Not covered: an answer that ignores a tool result that did
succeed, csv_summary's column names, and the overflow of a long note on a step card (left for now, by the user's choice).
