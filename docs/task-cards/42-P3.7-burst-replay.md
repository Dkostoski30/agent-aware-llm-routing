Decided 2026-11-12 with the user, planning P3.7:
- **Pattern burst-fan-out, not burst.** The converted trace has no parallel groups (0 of 6,318 calls) and burst adds no fan-out, so on burst the parallel rule would be on and never act. burst-fan-out has burst's arrivals with half of the later steps as 2 calls of one group; both variants get the same load.
- **The verdict is code.** `make experiment-compare` ends with it, from a `not_worse_tolerance` and the reference variant that `make experiment` copies from the experiment file into each `.meta.json`. Files whose tolerance or reference differ are refused. `experiment_compare.py` and its test join the files.
- **The spike ran on the default picker,** with its criterion fixed before the run: the burst overloads if, after at least 2 of the 4 bursts (120, 240, 360, 480 s at seed 6), a pod has more than 1 call waiting within 60 s. Result 2026-11-12: 5, 10, 12 and 11 at most, 357 calls, 0 failed, so the pattern is unchanged. From the second burst on both pods had 8-12 waiting, so the guard and the parallel rule, which move a call only to a pod at or under their threshold, will mostly find no room: the plugin then acts by affinity. A stated property of this load, not changed.
- **The picker's log is kept by make experiment,** for plugin variants only: the switch to the next variant, or back to the default after the last, restarts the picker and its log with it.

Claude's choices, stated while planning: the GPU log runs when any variant's profile is not sim, at the profile's `monitoring.scrape_interval_seconds` (5 s) so a sample lines up with a Prometheus reading; `runs_discarded` is the 4 runs before the first burst; the plugin variant is named `plugin`.

The whole routing plugin (affinity, overload guard, parallel spill) against the default picker on the same burst, on real

2026-11-12: it overloads, unchanged (see the decisions above).
