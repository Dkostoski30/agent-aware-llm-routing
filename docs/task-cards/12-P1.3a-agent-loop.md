answer; add one only if P1.6b shows rambling); GET /healthz comes in P1.3a-2 for P1.3b's readiness probe.

# P1.3a-1: Agent loop with a calculator tool, both D10 modes

Goal:
agent/ holds a package that runs one task as a chain of non-streaming LLM calls with a calculator tool, in either
D10 mode, with the D1 headers on every call. Proven by pytest with a mocked LLM.

Depends on:
P1.2 (the gateway's /v1 path, which the client calls)

Files allowed:
agent/pyproject.toml, agent/agent_runtime/ (__init__, config, tools, llm, loop), agent/tests/ (test_calculator,
test_agent_loop, test_agent_config), config/real.yaml, config/sim.yaml, config/demo.yaml (agent section),
pyproject.toml (uv workspace member, root dependency on agent, pytest pythonpath, mypy_path), uv.lock, versions.md,
docs/task-cards/12-P1.3a-agent-loop.md

Interfaces / outputs:
- run_task(task, run_id, seed, config, llm) -> RunResult (status done | failed, answer, error, steps,
  invalid_calls, messages).
- Every LLM call: POST <gateway>/v1/chat/completions with stream false (D6); model from model.name;
  chat_template_kwargs.enable_thinking false; sampling from agent.sampling; the run's seed if one was given.
  Headers: x-run-id, x-step (1-based, +1 on every call, retries included), x-expected-steps
  (agent.expected_steps_default until P2.4 derives it per task type), no x-parallel-group (no parallel calls yet).
  A non-2xx answer, a timeout (agent.llm_timeout_seconds, applied by httpx to each phase of the call; for a
  non-streaming call that is effectively the whole call) or a 200 whose body has no choices[0].message and
  finish_reason (LLMResponseError) fails the run with its message. finish_reason "length" fails the run at once in
  both modes, with an error naming model.max_model_len: there is no max_tokens cap, so a retry can only overflow again.
- The history keeps role, content and tool_calls of every assistant message, nothing else vLLM returns.
- agent.tool_choice (D10):
  required: every call sends tool_choice "required", so vLLM constrains the output to the tool schemas. The tool list
    includes final_answer {"answer": string}; calling it ends the run with that answer. A response without a tool
    call counts as an invalid call.
  auto: every call sends tool_choice "auto"; final_answer is not in the tool list. A text answer that contains a
    tool-call marker (<tool_call>), or an empty one (content null or "") with no tool call, counts as an invalid
    call: the reply stays in the history and a user message with the error follows. The error does not quote the
    marker back to the model. Plain, non-empty text with no marker is the final answer.
  Both modes: the tool calls of one response are checked and run in order, and the whole response is one step. A
    valid call runs and its result goes back as a tool message; an invalid call (unknown tool, arguments that are
    not JSON, a schema violation) goes back as a tool message with the error, which for an enum lists the allowed
    values. Caps: the run fails at the agent.max_invalid_calls-th invalid call, or after agent.max_steps calls
    without an answer (safety cap, D1).
- calculator tool: {"op": enum add|subtract|multiply|divide, "a": number, "b": number}. Division by zero comes back
  to the model as a tool error, not an exception, and is not an invalid call.
- Logs: stdlib logging with run-id and step on every line of a run (D12): run start, every call (with duration_ms
  and finish_reason), every invalid call with its reason, run end. The JSON formatter comes in P1.3a-2.
- New config keys (all profiles, each with a comment saying why): agent.tool_choice (demo: required, real and sim:
  auto, D10), agent.max_steps, agent.max_invalid_calls, agent.expected_steps_default, agent.llm_timeout_seconds,
  agent.sampling.{temperature, top_p, top_k} (Qwen3's recommended non-thinking values: 0.7 / 0.8 / 20),
  agent.system_prompt (the same text in every profile, worded for both modes).

Notes:
Tests first, asserting behavior, table-driven over both modes where the behavior is shared:
- auto: tool_choice "auto" is sent; final_answer is not in the tool list; a text answer ends the run; an invalid
  enum is retried with the allowed values in the message; a marker in text is retried; empty text is retried.
- required: tool_choice "required" is sent; final_answer is in the tool list; final_answer ends the run; plain text
  is an invalid call.
- both: a tool result is fed back; both caps fail the run; an HTTP error, a timeout (httpx.ReadTimeout) and a 200
  with body {} fail the run; finish_reason "length" fails the run; two calls in one response
  both run as one step; every call's headers validate against schemas/headers.v1.json (contract test, D12) with
  x-step increasing by 1; stream is false; model, sampling, thinking off and seed are sent; an invalid call is
  logged with its reason, run-id and step; every call is logged with duration_ms and finish_reason; calculator
  table tests; all three profiles load with the same prompt.
P1.3a-1 goes over the rule-1 size (~830 changed lines, ~380 of them table-driven tests and ~330 code); this was
accepted on purpose (2026-10-27).
The mocked LLM is httpx.MockTransport. The calculator stays after P2.1 as the cheap, predictable task of make smoke.
agent/ is a virtual uv workspace member (tool.uv.package = false, no build backend): uv installs its dependencies,
pytest and mypy find the package through pythonpath / mypy_path.
Dependencies (newest release at least two weeks old on 2026-10-27): httpx 0.28.1, pyyaml 6.0.3, jsonschema 4.26.0
(moves from dev to runtime); dev: types-PyYAML 6.0.12.20260906 (stubs for mypy strict), anyio 4.15.1 (its pytest
plugin runs the async tests; already a dependency of httpx, pinned because the tests use it directly).

# P1.3a-2: Agent runtime service: run API, run history in Redis, JSON logs

Goal:
The P1.3a-1 loop runs behind a FastAPI app: POST /runs starts a task in the background, GET /runs/{id} reads it
back, and the run history goes to Redis after every step. Proven by pytest with a mocked LLM and an in-memory store.

Depends on:
P1.3a-1

Files allowed:
agent/ (pyproject.toml, agent_runtime/: new store and app modules, loop, tests), schemas/run-request.v1.json (new),
schemas/examples/run-request.v1.valid.json (new), schemas/examples/run-request.v1.invalid.json (new),
schemas/tests/test_schemas.py (new cases only), config/real.yaml, config/sim.yaml, config/demo.yaml (agent section),
uv.lock, versions.md, docs/task-cards/12-P1.3a-agent-loop.md

Interfaces / outputs:
- POST /runs, body run-request.v1: {"task": string, "seed": optional integer}, checked with jsonschema (422 if
  invalid). Answers 202 {"run_id"} (run-<12 hex>) and runs the task in the background. GET /runs/{run_id}: status (running | done |
  failed), the answer, the steps (built from the stored messages) and the invalid-call count; 404 if unknown.
  GET /healthz: 200 {"status": "ok"}, for P1.3b's readiness probe. P1.6a adds optional files to run-request.v1;
  nothing else reads it before then.
- Redis (D7): thesis:run:<id> (hash) holds the run's metadata (status, task, step, expected_steps, invalid_calls,
  answer, error, timestamps), and thesis:run:<id>:messages holds the full message list as JSON, both written in one
  transaction after every step, so P4.4 can continue a run on another pod from it. TTL agent.history_ttl_seconds.
- Logs: JSON lines; every line of a run has run-id and step (D12).
- New config key: agent.history_ttl_seconds (all profiles, with a comment saying why).
- Addresses come from environment variables that the P1.3b manifest sets: THESIS_CONFIG, GATEWAY_URL, REDIS_URL,
  THESIS_SCHEMAS_DIR. They are addresses, not tunables.

Notes:
Tests first: POST /runs -> 202 and GET /runs/{id} -> done; an invalid body -> 422; an unknown id -> 404; /healthz;
the store holds the expected metadata and messages after every step; run-request examples and rules in
schemas/tests. The store in tests is an in-memory class behind the same interface as the Redis one (no fakeredis),
so the Redis store is first exercised by make agent-check in P1.3b.
Dependencies: fastapi 0.143.0, uvicorn 0.54.0, redis 8.1.0 (newest releases at least two weeks old on 2026-10-27).
Decided while planning and building (2026-10-27): agent.history_ttl_seconds is 86400 (a demo or experiment day;
P3.13's step view loses older chats' steps). It is a field of AgentConfig, so test_agent_loop.py's make_config fixture
gains one argument (no assertion changed). The loop takes an optional on_step callback, awaited after every step that
leaves the run going; the service saves the record and messages there, and the final state after run_task returns.
The JSON formatter lives in its own module, agent_runtime/logs.py, used by main() and its test; uvicorn runs with
log_config=None so its lines are JSON too, minus its color_message field. GET /runs/{id} returns run_id, status,
task, answer, error, expected_steps, invalid_calls and steps: one entry per assistant message (so entry n is x-step
n) with content, tool_calls [{name, arguments, result}] and the error the runtime sent back for a rejected reply.
An exception the loop does not turn into a failed run (a bug, Redis down) is not caught (CLAUDE.md rule 6): uvicorn
logs it and the run stays running until its TTL. The Redis client is created with decode_responses=True; the run
starts through FastAPI BackgroundTasks after the running record is saved, so a GET right after 202 never gets 404.
