# P1.3a: Agent runtime v0, the loop (tested with a mocked LLM)

Goal:
agent/ holds a FastAPI app that runs one task as a chain of non-streaming LLM calls with a calculator tool, in either
D10 mode. Every call carries the D1 headers and the run history goes to Redis. Everything is proven by pytest with a
mocked LLM and an in-memory history store; nothing runs in the cluster yet (that is P1.3b).

Depends on:
P1.2 (the gateway's /v1 path, which the client calls)

Files allowed:
agent/ (new: pyproject.toml, the package, tests), schemas/run-request.v1.json (new),
schemas/examples/run-request.v1.valid.json (new), schemas/examples/run-request.v1.invalid.json (new),
schemas/tests/test_schemas.py (new cases only), config/real.yaml, config/sim.yaml, config/demo.yaml (agent section),
pyproject.toml (uv workspace member, pytest paths), uv.lock, versions.md, docs/task-cards/12-P1.3a-agent-loop.md

Interfaces / outputs:
- POST /runs, body run-request.v1: {"task": string, "seed": optional integer}. Answers 202 {"run_id"} and runs the
  task in the background. GET /runs/{run_id}: status (running | done | failed), the answer, the steps and the
  invalid-call count. P1.6a adds optional files to run-request.v1; nothing else reads it before then.
- Every LLM call: POST <gateway>/v1/chat/completions with stream false (D6); model from model.name;
  chat_template_kwargs.enable_thinking false; sampling from agent.sampling; the run's seed if one was given.
  Headers: x-run-id (run-<12 hex>), x-step (1-based, +1 on every call, retries included), x-expected-steps
  (agent.expected_steps_default until P2.4 derives it per task type), no x-parallel-group (no parallel calls yet).
- agent.tool_choice (D10):
  required: every call sends tool_choice "required", so vLLM constrains the output to the tool schemas. The tool list
    includes final_answer {"answer": string}; calling it ends the run with that answer.
  auto: every call sends tool_choice "auto". A tool call is checked against that tool's JSON schema; an invalid call
    goes back to the model with the error and the allowed values. A text answer that contains a tool-call marker
    (<tool_call>) counts as an invalid call. Plain text with no marker is the final answer.
  Both modes: a valid call runs and its result goes back to the model. Caps: agent.max_steps (safety cap, D1) and
  agent.max_invalid_calls; hitting either one marks the run failed.
- calculator tool: {"op": enum add|subtract|multiply|divide, "a": number, "b": number}. Division by zero comes back
  to the model as a tool error, not an exception.
- Redis (D7): one key holds the run's metadata (status, task, step, expected_steps, invalid_calls, answer,
  timestamps), and one holds the full message list after every step, so P4.4 can continue a run on another pod
  from it. Key prefix thesis:run:, TTL agent.history_ttl_seconds.
- Logs: JSON lines; every line of a run has run-id and step (D12). Every invalid call is logged with its reason.
- New config keys (all profiles, each with a comment saying why): agent.tool_choice (demo: required, real and sim:
  auto, D10), agent.max_steps, agent.max_invalid_calls, agent.expected_steps_default, agent.history_ttl_seconds,
  agent.llm_timeout_seconds, agent.sampling.{temperature, top_p, top_k} (Qwen3's recommended non-thinking values:
  0.7 / 0.8 / 20).
- Base URLs (gateway, Redis) come from environment variables that the P1.3b manifest sets. They are addresses,
  not tunables.

Notes:
Tests first, asserting behavior, table-driven over both modes where the behavior is shared:
- auto: a text answer ends the run; an invalid enum is retried with the allowed values in the message; a marker in
  text is retried.
- required: tool_choice "required" is sent; final_answer ends the run; final_answer is in the tool list only in this
  mode.
- both: a tool result is fed back; both caps fail the run; every call's headers validate against
  schemas/headers.v1.json (contract test, D12) with x-step increasing by 1; stream is false; the history store holds
  the expected messages after a run; calculator table tests; POST /runs -> 202 and GET /runs/{id} -> done.
The mocked LLM is httpx.MockTransport; the store is an in-memory class behind the same interface as the Redis one
(no fakeredis). The calculator stays after P2.1 as the cheap, predictable task of make smoke.
Dependencies (listed with exact versions in the plan; approving the plan approves them): fastapi, uvicorn, httpx,
redis, jsonschema (moves from dev to runtime), pyyaml. Each is the newest release at least two weeks old.
