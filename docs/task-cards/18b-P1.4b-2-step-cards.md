# P1.4b-2: Live step cards

Goal:
The UI's run view shows each step card as it lands over GET /runs/{run_id}/events (P1.4b-1), then the answer.

Depends on:
P1.4b-1

Files allowed:
ui/ (run route and its components), docs/task-cards/18b-P1.4b-2-step-cards.md

Interfaces / outputs:
- The run events of schemas/run-events.v1.json through the dev server's /api proxy. The UI uses the browser's
  EventSource; no new dependency. It closes the source on the end event (otherwise the browser reconnects to a
  finished run forever); a run event resets the view, so a reconnect redraws the run from its replay.
- UI components ported from docs/design-system/components: RunHeader, StepCard, Status, Answer. The step line reads
  "Step 3 · 5 expected", never "3 of 5" (README: Content). Pod and cache badges come in P2.6; the Answer/Steps tabs
  come with the step table (P2.6).

Notes:
The end event's steps counts LLM calls sent, including one that failed without an answer; such a call has no step
event. A run that fails on its first call sends run, then end with steps 1 and no step card, so the UI counts the
step events it shows instead of using steps.
Tests first: cards render in arrival order; the answer slot fills on the end event; a run event after a reconnect
replaces the cards instead of adding to them. The spec checks the UI's event types against
schemas/run-events.v1.json, as runs.spec does for run-request.
Decided 2026-10-28 (the user approved going straight to code): the event handling and card logic are pure functions
in runs/run-view.ts, tested apart from the screen; EventSource sits behind an injection token (OPEN_EVENT_STREAM) so
the service is tested with a fake stream. Cards while running: the landed steps, then the call in flight ("Waiting
for the model", running) and dashed "Not started" cards up to x-expected-steps; once the run ends, only the steps
taken. A step the runtime sent an error back for (invalid call, tool error, rejected text reply) is retried, with
the error as its note and an "error" tag (confirmed with the user: "retry n" stays for pod-failure retries, P4.4).
A step with no tool call reads "Text reply". The header shows the elapsed
time once the run is over (no ticking clock while it runs). A failed run gets the Status chip ("Failed") in the header
and a fail notice with the error instead of the answer; Status is otherwise the pod chip of the cluster panel
(P3.11). The answer is plain text with its line breaks, never HTML. Left for later: the top bar's trotting horse while
a run goes, the follow-up composer dock (chats, P3.13), the step detail sheet, answer citations (the model writes
none yet).
Review 2026-10-28: the call in flight is numbered after the last landed step (not by counting), the run id is
URL-encoded, the lost-stream notice and comments say what can cause it. Known limits: after a lost stream the header
still trots and the running card stays (Phase 6 polish: no stuck spinners); a step cut off at model.max_model_len
shows its never-run calls as done, only the fail notice says why; RunScreen reads its id once, so a route that reuses
it for another run (chats, P3.13) must re-watch.
