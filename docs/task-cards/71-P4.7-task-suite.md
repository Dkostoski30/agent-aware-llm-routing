# P4.7: practical task suite, the 3 demo scenarios 10 times each through the chat

Added 2026-11-23, written while P4.8b's training ran.

Goal:
A command that sends each demo scenario's questions through the chat path (app backend, agent runtime, gateway, demo
pod), scores every answer, and writes the success table the thesis cites as proof of practical use.

Depends on:
P4.8 (committed 26e3104): the routing step and the chat path. Not on P4.8b: demo has no adapter.

Decisions (the user, 2026-11-23):
1. **5 questions x 2 seeds per scenario**, on the fixtures the demo trace already uses, scored like the go/no-go.
   (Offered: the UI cards' prompts x 10; 10 new questions each.)
   - CSV takes the go/no-go's five on `sales.csv`, `two-step` included. Demo got `two-step` wrong 4/4 in P4.8's
     go/no-go, so CSV likely ends at 8/10. That would be a red result, not a reason to pick other questions.
   - Contracts and support get five each: record-demo's four, plus one of a kind it already has.
2. **A fresh chat per run:** each run is one message in a new chat, with its scenario's files attached. That gives
   30 independent samples. (Offered: one chat per scenario, whose later turns carry the earlier ones as history.)

Proposed while planning (Claude; the plan's approval approves these):
- **The questions and what a correct answer contains.** CSV answers are scored by number, as in
  `demo-go-no-go.yaml`. Text answers must contain these texts, case and spacing aside (`go_no_go.CONTAINS`). They are
  the texts the generator scores the same kinds by (`finetune_data._contains`).

  | Scenario | Question | Expected call | Must contain |
  |---|---|---|---|
  | contracts | What changed in the termination clause between contract-2025.txt and contract-2026.txt? | diff_clauses | 60 days |
  | contracts | Compare the fees clause of contract-2025.txt and contract-2026.txt. | diff_clauses | 1,350 EUR |
  | contracts | What does the confidentiality clause of contract-2026.txt say? | extract_clauses | two years |
  | contracts | Read me the services clause in contract-2025.txt. | extract_clauses | monthly sales report |
  | contracts | What does the termination clause of contract-2026.txt say? | extract_clauses | 60 days |
  | support | A customer asks about our returns policy for order 1041. Write the reply. | draft_reply | 1041, Returns, 2026-11-05 |
  | support | Draft a reply for order 1042 that applies our damaged items policy. | draft_reply | 1042, Damaged items, 2026-10-29 |
  | support | What is the status of order 1043? | get_order | shipped |
  | support | What is the status of order 1041? | get_order | delivered |
  | support | What does the refunds policy say? | get_policy | 5 working days |

  A test runs each question's expected call through the agent's own tools on the fixtures and checks that the
  result holds every text. So no question asks for something the tools cannot give, as the generator checks its
  own.
- **The mode is the demo profile's** (`agent.tool_choice: required`), with no switching: the go/no-go chose it.
- **How a run goes:**
  1. One user is registered for the whole suite (an `.invalid` address, as `make smoke` does).
  2. The runner talks to the app pod's IP, as `go_no_go` talks to the agent's.
  3. Each run creates a chat, sends the question with its files and seed, and reads `GET /chats/{id}` until the
     answer is no longer running. It gives up after `agent.max_steps` x `agent.llm_timeout_seconds`, as go_no_go
     does.
  4. It reads the run's steps through the app's `GET /runs/{id}` and scores them with `go_no_go.is_correct`.
  5. The session cookie is `Secure`, so the runner sends it in a header itself over plain HTTP to the pod.
- **What it writes:** one CSV row per run, with scenario, question, seed, correct, step 1's pick, steps, invalid
  calls, duration, answer, status and error. It goes to `experiments/results/task-suite-<hash>-<agent tag>.csv`
  (D11). Then the success table: per scenario, right out of 10 and the picks, then whether every scenario reached 9.
- **Refused before any run:** a cluster whose agent isn't serving the demo profile's model (go_no_go's
  `served_differs`), and a question whose expected value or texts can't be computed from its files.
- **If a scenario misses 9/10,** the table goes in the log as it is, and the fix comes back to the user as its own
  task before Gate 4 (rule 8).

Decided while coding (Claude, 2026-11-23):
- **`go_no_go.ready_pod_ip` takes the Deployment's name** (default `agent`), so its error names the app pod when the
  suite asks for that one, instead of the runner copying it.
- **Dates in the expected texts are quoted** in the YAML, which otherwise reads `2026-11-05` as a date; the
  reachability test caught it.
- **A run still going after the timeout stops the suite** (`RunTimedOut`) instead of scoring a timeout row: only a
  stuck cluster runs that long.

Run (2026-11-24): csv 8/10, contracts 10/10, support 10/10; step 1 picked right in 30 of 30. Both misses are
`two-step`, as predicted. Logged as a limit of the untrained 1.7B, with no new task (the user, 2026-11-24; offered: a
