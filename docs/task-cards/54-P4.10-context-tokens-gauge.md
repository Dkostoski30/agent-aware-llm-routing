# P4.10: The run tracker exports the context its runs hold

Added 2026-11-16 (Claude's proposal, planned at the user's request). P4.9 measures cache pressure after a replay; this makes its numerator a live number, so the panel (P4.11) and KEDA (P4.12) can read it. It sits beside remaining work. D2's sum does not change.

The risk to know before building: the two sources learn a call's prompt tokens at different moments. The replayer knows them before it sends (the plan's count, which it already checks against the server's). The agent runtime knows them only from the reply's `usage`. So an agent run adds 0 during its first call and trails by one call after that. That is a stated limit, not something to close here: counting before the send needs vLLM's `/tokenize`, which is P4.8's.

Decided 2026-11-20 with the user, while planning:
- The done-when's comparison with the replay's file is a script, not a second terminal (rule 9): `make context-check`, in
  `loadgen/load_generator/context_check.py`, run after the replay. It reads `sum(thesis_context_tokens)` over the replay's window
  through the API server's proxy to Prometheus, as `experiment.py` does, and judges three things: the highest sample equals the file's
  sum for some moment within one scrape of it, samples where the file has no run active read 0, and there is no series after the
  replay. The file's sum at a moment uses the wall clock (`ts_start`, `duration_ms`), since the samples carry the VM's clock as the
  replayer does. Added to the files: that module, `loadgen/tests/test_context_check.py`, `Makefile` (context-check).
- A run P4.4 resumes starts with the prompt tokens of its last saved call, and then trails by one call like any agent run.

Claude's choices, stated with the plan: a fanned-out step counts once, its calls sharing one prompt (P4.9's rule); a retried call
sends the same prompt, so the figure does not change; in the replayer a run with a failed call keeps its figure until the step's
other calls are done and the run ends, where P4.9 stops at the failed call's start, at most one step apart. sim scrapes every 5 s
(`config/sim.yaml` scrape_interval_seconds), so "within one scrape" is 5 s there.

Built 2026-11-20: `RunTracker.context` and `context_tokens`, the third gauge read under the same lock; the agent loop counts each
reply's usage.prompt_tokens and seeds a resumed run with its latest saved count; the replayer counts each step's planned prompt
beside `stepped`. `make context-check` (wall-clock windows of one scrape either side; series allowed until two scrapes after the last
call, read until four). The tests' lock check is a lock that lets a run arrive right after its release, since a second thread never
hit the gap under the GIL (0 of ~100,000 reads with a split read); 21 mutants, all killed.

Run 1 (2026-11-20, sim, p4-10-context-steady-long.jsonl, 81 calls, 0 failed): `make context-check` failed on 2 of 282 readings, both
artefacts of the check, not of the gauge. It read `sum(thesis_context_tokens)` with a range query on a 5 s grid, whose value at t is
the latest scrape before t, and scrapes slipped up to 7.6 s apart: the reading at 560 s was a 6.9 s old scrape, right for its own
time. And WSL steps the VM's wall clock +1.7 to +2.0 s every few minutes (6 steps in 18 min), so a file's call end, wall-clock start
plus monotonic duration, lags the clock Prometheus stamps with; the reading at 470 s was a run the file ended 0.7 s before the scrape.
Decided 2026-11-20 with the user: judge Prometheus's raw scrape samples of the replayer's own series,
`thesis_context_tokens{job="replayer-metrics"}`, at their own times (the file holds the replayer's runs alone); window and verdicts
unchanged. On the same replay's samples, read-only: 267 of 267 scrapes equal a file sum within one scrape, no failure.

The shared run tracker serves a third gauge, thesis_context_tokens: the sum over active runs of the prompt tokens of their latest call.
The agent runtime and the replayer both feed it.

Depends on:

- RunTracker.context(run_id, prompt_tokens): the run's latest call has this many prompt tokens. A run that was never started, or has

  with no count leaves the run's figure as it was.
