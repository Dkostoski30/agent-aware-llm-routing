# P3.5: Overload guard

The picker reads each pod's `WaitingQueueSize` from vLLM's `vllm:num_requests_waiting`, refreshed every 50 ms by default (`--refresh-metrics-interval`, read in v0.11.0). On a real pod this queue also holds calls waiting for KV blocks, the waiting behind every p95 miss in P2.9.

Runs on sim (decided 2026-11-09): this task proves behaviour, and P3.7 makes the latency claim.

```
# P3.5: Overload guard

Goal:
A pinned run stays pinned unless its pod is overloaded: over the queue threshold one call spills to another pod and the pin
stays; only sustained overload moves the pin. A short spike never moves it.

Depends on:
P3.3

Files allowed:
gateway/runrouter/, config/real.yaml, config/real-plain.yaml, config/sim.yaml, config/demo.yaml (routing section),
infra/routing-values.sh, experiments/log.md, PLAN.md (P3.5 row), docs/task-cards/40-P3.5-overload-guard.md

Interfaces / outputs:
- With routing.overload_guard: pinned pod's queue over routing.overload_queue_threshold, and another candidate at or under
  it: the candidates without the pinned pod (spill). Every candidate over it: the pinned pod, since moving gains nothing and
  loses the cache.
- Over the threshold without a break for routing.overload_sustained_seconds: the pin is dropped, so PreRequest binds the
  next call's pod (remap). Back at or under the threshold: the timer resets.
- routing.overload_queue_threshold, first guess 1 (one call already waiting for a slot or KV blocks);
  routing.overload_sustained_seconds, first guess 10 (several p50 calls of 2.3 s, P2.9, so one long call is not "sustained").
  Both commented as first guesses; P3.7 measures them.
- JSON log lines with reason spill and remap, with run-id, step, pod and queue. A counter thesis_picker_decisions_total
  {decision} on the picker's metrics port.

Notes:
Tests first, table-driven with a fake clock: under the threshold stays; a spike spills and keeps the pin, and the next call
returns; sustained remaps once; a dip resets the timer; all pods overloaded stays; guard off never spills. Under sustained
overload a spill loses the cache but prefill is cheap (0.146 ms per uncached token against seconds in a queue, P2.8c), so
spilling is expected to help. "routing on" below means bash infra/set-routing.sh sim <a file with the flags> first.

Done when (I run this myself):

make down, make up PROFILE=sim
make replay TRACE=<converted trace> PATTERN=steady-long PROFILE=sim OUT=<new file>, routing on  -> 0 spill lines if the queue never passed the threshold
make replay TRACE=<converted trace> PATTERN=burst PROFILE=sim OUT=<new file>, routing on        -> spill lines > 0; every remap line follows at least overload_sustained_seconds of spills for that pod

experiments/log.md
```
