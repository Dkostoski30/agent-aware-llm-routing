# P5.4a: The cluster panel follows Start and Kill

Planned 2026-11-27, on branch `feature/phase-5`, after P5.4's code (card 78) and before its run.

Goal:
The user watched the panel on real while pressing Start and Kill (2026-11-27): a killed pod stayed on the panel and a
new replay's numbers stayed stale for several seconds. The cause is the panel's design (P3.11): its pod list came from
kube-state-metrics through Prometheus (5 s scrapes), the panel read `/cluster` every 5 s, and a press did not make it
read again, so a kill could show up to ~10 s late. This card makes the panel follow a press within one read.

Depends on:
P3.11 (card 47, `GET /cluster` and the panel), P4.6a-c (the buttons, the runner, the kill guard), P5.4 (card 78, the
rehearsal that now checks it).

Decided (the user, 2026-11-27):
1. **A card now, before P5.4 closes** (recommended). Offered: only a re-read after a press; Phase 6's polish list; a
   stated limit.
2. **The pod list from the Kubernetes API** (recommended), with the app pod's own ServiceAccount; queues, running
   calls, remaining work and cache pressure stay on Prometheus, word for word Grafana's. Offered: stay on Prometheus.
3. **One read every 5 s and one at once after a press** (recommended). Offered: the pods every 1 s on their own.
4. **Order:** P5.4's code committed first, then this card, then card 81 (a charts view), then P5.4's one run on the
   finished UI.

Claude's choices:
- **Least access:** the ServiceAccount `app` may `list` pods in `default` and nothing else (Role `app-pods`); Kill
  stays with `make demo-runner` on the host. The app reads the token for every request, since the kubelet replaces it
  in its file before it expires, and checks the API's certificate against the ServiceAccount's CA.
- **The same states:** each listed pod goes through P3.11's `pod_state` (phase, Ready condition, deletion time); a pod
  not yet scheduled has no conditions and is starting. The label selector is the runner's (`app.kubernetes.io/name=vllm`).
- **Outages:** the Kubernetes API down or unreachable is a 503 with `poll_seconds`, as Prometheus down is, with the
  detail `Kubernetes did not answer`; a 4xx (a missing Role) raises as the bug it is.
- **The re-read:** the demo controls emit `pressed` once the runner took a press (not on a refusal); the panel drops a
  read in flight, which may have left before the press, and its timer, and reads at once. The kill's answer comes after
  the delete, so that read no longer lists the pod.
- **The rehearsal checks it:** after Kill, the panel must stop listing the killed pod within `pod_gone_seconds` (5 s,
  the panel's interval), or the round fails; each round records `gone_from_panel_after_s`.
- **Tests:** the existing cluster tests that set the pods through kube-state-metrics answers now set them through the
  fake Kubernetes API, with the same assertions; Grafana's pressure-panel test keeps its PromQL text, now in the test,
  since the app no longer sends it. The four other app test files pass a refusing Kubernetes client beside their
  refusing Prometheus one.
- **Limit kept:** queues, running calls and remaining work still trail by one Prometheus scrape (up to 5 s), since they
  exist only as metrics; the panel's pod list may now lead Grafana's (still kube-state-metrics) by a scrape.
