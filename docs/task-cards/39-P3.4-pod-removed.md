# P3.4: A pinned pod disappears

Decided 2026-11-09 with the user: PLAN.md's "no request fails in a replay with a pod deleted" can't hold, because a call running on the deleted pod dies and a replay never retries (P2.3's decision; retry is P4.4). The check is narrowed: **no call sent after the pod left the pool fails, and the run's later steps land on another pod.** Calls that were running on it are counted and reported.

```
# P3.4: A pinned pod disappears

Goal:
When a pinned pod leaves the pool, the runs pinned to it continue on another pod, and a replay with a pod deleted proves it.

Depends on:
P3.3

Files allowed:
gateway/runrouter/, loadgen/load_generator/pod_removed.py (new), loadgen/tests/test_pod_removed.py (new), Makefile

docs/task-cards/39-P3.4-pod-removed.md

Interfaces / outputs:
- A pin whose pod is not among the candidates passes every candidate through, and PreRequest binds the run to the new pod.
  A JSON log line with reason remapped.
- make pod-removed EXPERIMENT=experiments/pod-removed.yaml: a replay in-process, kubectl delete pod of one pod at
  delete_after_seconds, then a report of the calls in three groups: finished before, running at the delete, sent after
  the settle time. The replay's stdout is kept beside its result, since a failure's reason is printed only there (P2.3)
  and trace.v1 has no field for it.
- experiments/pod-removed.yaml: profile sim, routing {plugin: true, affinity: true}, trace, pattern, seed, delete_after_seconds, settle_seconds (a first guess of
  5: the picker's informer plus the 2.5 s the VM's wall clock can step, P2.3, since kubectl's and ts_start are wall clock).

Notes:
Tests first: removed-pod remap (Go, table-driven); the three groups from known lines (Python). P4.4 reuses the delete and the
report. The replay's default deadline still applies: long task types fail first at 120 s, so a late failure there is that,
which the report's reason shows (P2.3). Runs on sim, where a restart costs no model load.
```
