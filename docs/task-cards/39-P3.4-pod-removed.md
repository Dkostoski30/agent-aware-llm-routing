# P3.4: A pinned pod disappears

Decided 2026-11-09 with the user: PLAN.md's "no request fails in a replay with a pod deleted" can't hold, because a call running on the deleted pod dies and a replay never retries (P2.3's decision; retry is P4.4). The check is narrowed: **no call sent after the pod left the pool fails, and the run's later steps land on another pod.** Calls that were running on it are counted and reported.

Decided 2026-11-11 with the user, planning P3.4: calls sent between the delete and the end of the settle are a fourth
group, counted and not judged (the picker may still send one to the deleted pod before it learns of the delete, which
answers 503); the load is steady-long at seed 6 on the converted trace with the delete at 120 s (3 runs active then in
P3.1's sim replay; its load is measured, so the one pod left for the replacement's 140 s start should not push calls past
the deadline); `experiment.py` joins the files so `set_routing` is shared, not copied; the report reads the picker's log:
exactly one remapped line from the deleted pod per tested run is part of the pass, and the Run ended lines are counted
(the end of run had never been seen on the cluster).

Found while planning: both traces' steps follow each other within a few ms (median gap 2 ms), so a pinned run is nearly
always mid-call when its pod goes. llm-d-inference-sim v1.0.0 drains on SIGTERM (up to 30 s for the calls it runs, then
5 s for its HTTP server; new calls get 503 "server is shutting down"; /health/ready does not change), so those calls
likely finish and the run's next step is the remap. llm-d-router v0.11.0 drops a pod from the pool once its deletion is
asked for (IsPodReady checks the DeletionTimestamp), not when it exits. The plugin keys pins by pod name, as the picker's
pool does (an InferencePool selects pods in its own namespace).

First run 2026-11-11 (pod-removed-07fcbf93ea76): 153 calls, 0 failed, but nothing tested. The first Ready pod by name
held no live run at 120 s (both active runs were on the other pod), and the picker's log names endpoints
`<pod>-rank-0`, which the report compared with plain pod names. Decided with the user: the run now deletes the Ready
pod holding the most live pins in the picker's log at delete_after_seconds (ties by name); the report maps endpoint
names to pods, and counts as affected only runs not finished by the delete.

Second run 2026-11-11 (pod-removed-346f89bc516e): passed, 2 runs remapped, 0 of 126 calls after the settle failed
(experiments/log.md). It counted set-routing's probe as a live pin, since kubectl's --since-time returned a line logged
before the window; live_pins now checks each line's own timestamp too, fixed without a rerun (decided with the user), as
the choice on that log is the same.

Fresh-eyes review 2026-11-11, all fixed without a rerun (decided with the user): a pod that outlives the wait leaves
gone_ms null instead of ending the run without a report; a delete thread that dies is named; the first switch is inside
the try; "running at the delete" counts the calls on the deleted pod apart; tests for those paths and main. For P3.6: two
calls of one run that pass the filter together with no pin may go to two pods, the second logged remapped though no pod
left; nothing sends that today (the replayer fans out steps 2..n only).

Second review 2026-11-11: no correctness bug. For P4.4, which reuses the delete and the report: fetch and keep the
picker's log before anything after the replay can fail (the finally's set-routing restarts the picker and loses it), and
write what is known on an error; check the cluster runs the file's profile; keep a dead delete thread's traceback with
the result; tell a kubectl wait error from its timeout.

# P3.4: A pinned pod disappears

Goal:
When a pinned pod leaves the pool, the runs pinned to it continue on another pod, and a replay with a pod deleted proves it.

Depends on:
P3.3

Files allowed:
gateway/runrouter/, loadgen/load_generator/pod_removed.py (new), loadgen/tests/test_pod_removed.py (new), Makefile
(pod-removed), experiments/pod-removed.yaml (new), experiments/log.md, experiments/results/, PLAN.md (P3.4 row),
docs/task-cards/39-P3.4-pod-removed.md, loadgen/load_generator/experiment.py (set_routing as a module function, added
2026-11-11)

Interfaces / outputs:
- A pin whose pod is not among the candidates passes every candidate through, and PreRequest binds the run to the new pod.
  A JSON log line with reason remapped and from, the pod the run left.
- make pod-removed EXPERIMENT=experiments/pod-removed.yaml: a replay in-process, kubectl delete pod of one pod at
  delete_after_seconds, then a report of the calls in four groups: finished before, running at the delete, sent during
  the settle (counted, not judged), sent after the settle time. Runs pinned to the deleted pod at the delete are listed;
  those with a call sent after must each have one remapped line from it in the picker's log, kept beside the result with
  the Run ended lines counted. The replay's stdout is kept beside its result, since a failure's reason is printed only there (P2.3)
  and trace.v1 has no field for it.
- experiments/pod-removed.yaml: profile sim, routing {plugin: true, affinity: true}, trace, pattern, seed, delete_after_seconds, settle_seconds (a first guess of
  5: the picker's informer plus the 2.5 s the VM's wall clock can step, P2.3, since kubectl's and ts_start are wall clock).

Notes:
Tests first: removed-pod remap (Go, table-driven); the four groups, the affected runs and the verdict from known lines (Python). P4.4 reuses the delete and the
report. The replay's default deadline still applies: long task types fail first at 120 s, so a late failure there is that,
which the report's reason shows (P2.3). Runs on sim, where a restart costs no model load.

make pod-removed EXPERIMENT=experiments/pod-removed.yaml
                                             -> group "sent after": 0 failed; every affected run's later steps on the other
                                                pod; group "running at the delete": a count, any number

Record in:
experiments/log.md
