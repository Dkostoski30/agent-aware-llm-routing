# P2.4: AgentProcessBench converter and expected-steps per task type

Spike 2026-11-03, the card's step 1, read-only: the dataset is usable, with the problem below.
- Where: huggingface.co/datasets/LulaCola/AgentProcessBench, revision cd81f326aece8b0a3f6359e20df370690d3a98bf, 40 MB, 4 subsets of
  250 runs. MIT on Hugging Face; the authors' GitHub repo states no license; the source benchmarks' own terms are not checked. No
  dataset text enters the repo, so the fixture is written by hand and the trace holds counts only.
- A trajectory holds its full messages, tool definitions, tool calls, a data_source, step labels and a final label. No token counts
  and no timings: tool_metrics has status and text length only. Its 8,509 assistant messages are the paper's 8,509 annotated actions.
- Only 1,431 of 8,259 calls fit max_model_len 4096, and none of tau2's: its first prompts alone are 4,568-6,773 tokens. Keeping only the
  runs that fit leaves 314, median 2 steps, 28 with 5 or more, which misses the card's goal. (Counted with the bfcl decision below; the
  spike's own figures were a little off, experiments/log.md.)
- /tokenize gave the local tokenizer's count on 8 of 8 prompts compared, accepts prompts over the limit, malformed tool arguments
  (32 replies hold them), tau2's user messages with tool_calls and bfcl's tool messages without an id.

Decided 2026-11-03 with the user, after the spike:
- Scale per task type. One factor on a type's prompts and replies, from the size of its run at keep_share 0.9, larger runs dropped.
  The steps of a kept run, its growth and each call's ratio of prompt to reply stay the dataset's, which scaling only the prompts would
  break. Uncached tokens per reply token do rise, since the chat template's 9 tokens and a block's remainder do not scale. Token counts are
  no longer literal, a limitation the thesis states. These traces spend more of a call on prefill than the demo's, so caching has more to
  gain than P2.2b's ~9%: that comes from the dataset's proportions, and is stated too.
- The gap is the median tool time of the P2.2b recording, 2 ms, on every later step, the card's rule. Measured and true of our
  Python tools; a limitation, since search tools and user turns (28% of later steps follow one) would take seconds, so a replay runs
  heavier than those agents did. Assumed times per kind were set aside as numbers no measurement backs.

Decided in plan mode, approved 2026-11-03:
- One assistant message is one call: several tool calls in a reply stay one call of the model, so no parallel_group. A multi-turn
  trajectory is one run, since its context is shared. tau2's first assistant message, the same fixed greeting in all 250 runs before any
  user message, is no call of the model but stays in the history. tau2's three domains are three task types: each has its own system
  prompt and tools.
- A run with a reply over max_reply_tokens after scaling (265, 60 s at P2.2b's speed, half the deadline) is dropped and counted.
- expected_steps is the median calls per run, rounded up, since a remaining-work figure that is too low starts a scale-up late. Every
  run of the trace counts, and dropped runs do not, which lowers tau2_airline, tau2_retail and bfcl by 1. A failed run counts: it uses the
  GPU too, and the median of all and of the runs labelled good differ by at most 1 step. So a trace
  needs no run status, which settles what P2.2b left to this card. The medians rest on few independent runs: about 200 distinct tasks
  with 5 samples each, about 17 distinct demo runs.
- The profiles hold the values under agent.expected_steps_by_type. make convert prints them to paste, since PyYAML would drop a
  profile's comments, and a test fails until they agree with the committed traces.
- A new pattern steady-long replaces steady in the done-when: a converted run was estimated at 49 s against a demo run's 22 s (P2.2b's
  fit), so steady's rate would likely overload the pods. A first guess at 0.02, meant as the same load as steady; it measured 1.68 calls
  in flight against steady's 0.70, which is stated, not a reason to change it here.
- The P2.2b trace stays as it is, so its replays keep sending x-expected-steps 2 until P4.8 re-records: right for csv and arithmetic,
  one too low for contracts and support. Editing it would break its name's hash and the committed comparisons.
- make convert checks only the model section of the running profile, not all of it as make record does: nothing else changes a count,
  and another edit to the profile would otherwise need a make up.

Decided 2026-11-03 with the user, after a fresh-eyes review of the first conversion:
- bfcl drops its tool list and its state snapshots. Its system message already lists every tool (250 of 250 runs, no other subset), so
  sending the definitions counted them twice; the first conversion wrapped them, on a misreading of their shape. Its mid-run `<state_info>`
  system messages (1,105, all bfcl's; 246 of its 250 runs end on one) look like the benchmark's record and not something the model read:
  inferred from the data. The first trace is superseded; the log keeps its replay as the "before".
- keep_share stays 0.9, and the loss of long runs is stated: runs of 30+ calls go from 30 to 8, the longest from 94 to 37. 0.95 would keep 16
  and 56, but with gaia_dev at factor 0.144 against 0.262, and every call of a type shrinks with it.
- A prompt keeps the length /tokenize gave it. A rule clamping a shrinking prompt changed nothing in the trace, since the only prompt that shrinks is
  in a dropped run, so a test on the committed trace checks it instead.
- The done-when's seed comes from a rule, not from looking at results: the first seed with 4-6 runs from each of hotpotqa, gaia_dev, tau2 and bfcl,
  checked with build_plan after the conversion. Seed 6.

Goal:
Long agent traces for the experiments: AgentProcessBench trajectories converted to trace.v1, so the replayer runs
them. The demo's own runs are short (2-4 calls, experiments/log.md P1.3b). expected_steps per task type comes from
recorded runs (D1) instead of agent.expected_steps_default.

P2.3

- Converter: one trace.v1 line per LLM call of a trajectory; prompt_tokens grows with the history (as P2.3 builds

- Gaps (D9): the median tool time of the P2.2b recording on every later step (decided above); the dataset has no timings.
- expected_steps: per task type from recorded runs (median, rounded up), written to config/ with a comment naming the

  it into its lines now, and the replayer sends what the lines hold.
- make convert EXPERIMENT=experiments/convert-apb.yaml: experiments/results/traces/convert-apb-<hash>-<revision>.jsonl and
  .meta.json beside it (each type's factor, dropped runs, calls, values). An existing trace is refused.
