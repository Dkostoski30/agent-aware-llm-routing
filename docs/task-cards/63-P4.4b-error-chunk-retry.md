# P4.4b: A vLLM error chunk with a 5xx code is retried like a 5xx reply

Added 2026-11-21. Follow-up to P4.4 (card 60), chosen by the user after P4.6a's real run (card 62, 2026-11-21): kill 1
force-deleted a vLLM pod whose engine died while its HTTP server still answered, and run 2's first call ended in an error
chunk inside a 200 stream, `{'message': 'EngineCore encountered an issue...', 'code': 500}`. P4.4's rule retries a lost
connection, a cut stream or a 5xx status; this was none of them, so the call was lost.

Read in the code before planning (Claude, 2026-11-21):
- `loadgen/load_generator/replay.py` `_chunk_of` raises `ReplyError` on any chunk with an `error`, and
  `send_with_retries` re-raises what `agent_runtime.retry.retryable` does not accept, which is every non-httpx error.
- The agent's own calls are not streamed (D6) and got real 500 statuses in P4.4's live check, so only the replayer needs
  this.
- vLLM v0.31.0 (source read 2026-11-21, tag v0.31.0): `entrypoints/openai/chat_completion/serving.py:926-931` turns an
  exception in the stream generator into `data: {ErrorResponse}` then `data: [DONE]`;
  `entrypoints/serve/engine/protocol.py:79-87` has `ErrorResponse = {"error": ErrorInfo}`, `ErrorInfo = {message, type,
  param, code: int}`; `entrypoints/serve/exception_handling/error_response.py` sets `code` from the HTTP status, 500 for
  a server-side error.

Decisions (the user, 2026-11-21):
1. An error chunk whose `code` is 500 or more is a 5xx reply; a 4xx code is not retried, as a 4xx status is not.
2. `replay.py` only: `agent_runtime/retry.py` stays as it is.
3. Done when the tests hold it; the live check is P4.6b's real run with a kill, logged whichever way the kill lands (a
   cut stream or an error chunk). (Offered: a demo rerun with kills until one hits an error chunk; a scripted check that
   kills only vLLM's engine process.)

Decided while planning (Claude, stated to the user):
- The replayer raises `httpx.HTTPStatusError` with a response of the chunk's code on the stream's request, so the shared
  rule judges it as it judges a status: 500 and up retried, a 4xx not, and the printed lines name the code. Changed
  while building: the plan raised it for 500 and up only, which repeated `retryable`'s threshold in `replay.py` (four
  mutants on it survived); the threshold now lives in `retry.py` alone.
- An error chunk stays a `ReplyError`, not retried, when its code is missing, not an int (a string or a bool) or the
  error is not an object. vLLM always writes an int; anything else is not a reply vLLM's source writes.
- No PLAN row of its own: a "P4.4b green" sentence on P4.4's row.

Files: `loadgen/load_generator/replay.py`, `loadgen/tests/test_replay.py`, this card, `experiments/log.md`, `PLAN.md`.

Done when: `make test` and `make lint` pass, with new tests that a 5xx error chunk is sent again and answered, that out of
retries it fails, and that a 4xx code, a missing code, a code that is not an int and an error that is not an object are
not sent again.
