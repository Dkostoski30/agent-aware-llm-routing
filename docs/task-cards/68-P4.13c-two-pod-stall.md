# P4.13c: two compiled real pods busy at once stall; find the cause, fix it, show it gone

Added 2026-11-23, after P4.13b (card 67, `experiments/log.md` 2026-11-23 · P4.13b). In validate-sim's real-2pods
variant both compiled pods, busy at once, generated about 1 token/s each for most of 40 minutes. Run completion p50
was 79.1 s against 28.4 on eager pods, and 2 calls failed. At 1 pod the same pods ran at 12.4 ms per token.

What the saved files show (Claude, 2026-11-23, from `experiments/results/validate-sim-f27264e942ba-*`):
- **Both pods started together.** They came from one deploy (ReplicaSet 6c4945cf88, created 10:17:04). They loaded the
  compile cache and began graph capture in the same second (10:19:44.97). Each logged `Graph capturing finished in
  27-28 secs, took 1.73 GiB`, and one batch size took 11.8 s. Every other compiled start on record logged 0.00-0.08 GiB
  in 12 s or less: P4.13's pods, which started one at a time, and the 1-pod variant.
- **The GPU filled then and stayed full.** nvidia-smi's memory went to 3,878 MiB at that moment and stayed at
  3,873-3,904 MiB to the end.
- **The stall looked like waiting, not work.** The GPU read 100% busy, 2-8% memory controller and about 35 W.
  Eager runs at full use read 45-52% and 46-60 W (`autoscale-real-1to2-a`, `routing-burst`). With one pod busy, the
  same run read 69%, 53% and 56 W.
- **Every compiled 2-pod measurement that ran well started its second pod beside a Ready first one:**
  - P4.13's spike: 28-30 ms per token.
  - P4.13b's `make calibrate` cells: 24-42 ms per token up to concurrency 8 and 3,584-token prompts. Their slow first
    tokens are calls waiting for KV, at a normal per-token time.
  - Calibrate's cold starts of both pods at once had a first call 1.7-4.3 s to its first token, against 0.9-1.5 s for a
    pod started alone.
- **Today, fixed 2-pod real pods start together.** `make vllm-deploy` (and `make up`) installs 2 replicas, and the
  experiment runner's restart (`infra/restart-vllm.sh`) recreates both at once, as the Deployment is `Recreate`.
  Autoscaling variants add the second pod later.

**The lead, not proven:** pods capturing graphs at the same moment end with more than the GPU's 4 GB. Windows' driver
then keeps the excess in system memory, which nvidia-smi under WSL does not show, and two busy pods wait on it. vLLM
under WSL reads the whole device's free memory (`config/real.yaml`, `kv_cache_memory_bytes`), so the 1.73 GiB may
count the other pod's memory too; the figure itself is not trusted.

**Not excluded: the load.** The replay's calls sample at temperature 0.6, top-k 20 and top-p 0.95 (the model's
`generation_config.json`) and carry tools, unlike calibrate's. The good runs differ from the bad one in both start
order and load.

Decisions (the user, 2026-11-23):
1. **Measure first:** the two starts on validate-sim's replay, then fix what the runs show. (Offered: fix the lead
   directly; real back to eager.)
2. **Windows' GPU memory goes in every real run's GPU log.** (Offered: only for this task's runs; nvidia-smi only.)
3. **The proof is the 2-pod pair only,** real and simulated back to back. Its verdict replaces P4.13b's 2-pod rows; the
   1-pod rows stay, since a lone pod's start does not change. (Offered: the full validate-sim.)

Decided while planning (Claude, stated to the user):
- **How Windows' memory is read.** `typeperf.exe` (Windows' own counter logger, called through WSL interop, as
  `make calibrate` already calls `powershell.exe` for the clock) is one process per run. It writes a CSV line per sample
  to `<stem>-windows-gpu.csv`, beside `<stem>-gpu.csv`. It logs `\GPU Adapter Memory(*)\Dedicated Usage` and
  `\GPU Adapter Memory(*)\Shared Usage` for every adapter, at nvidia-smi's interval, and starts and stops with
  nvidia-smi's log. If it ends early, that is reported as nvidia-smi's is. Shared usage rising while two pods run is
  the spill; staying flat rules it out.
- **The pre-check (below) passed, run by Claude after the user's go, 2026-11-23.** The counters exist under these
  names. typeperf wrote its lines to a file. The timeout's stop ended the Windows process. This Windows lists three
  adapters; the NVIDIA one is `luid_0x00000000_0x00011B7F`, whose 412 MB dedicated at idle matches nvidia-smi's
  ~400 MiB.
- **The computer's name is left out of the CSV (Claude, while coding).** typeperf names every column
  `\\<computer>\<counter>`, and the results are committed. When the log stops, the file keeps only typeperf's CSV
  lines, with LF line ends and no computer name. Before the run, a one-sample `typeperf -sc 1` checks the counters, as
  nvidia-smi's fields are checked.
- **`start` on an experiment variant:**
  - `together`, the default, is today's run: the restart starts every pod at once.
  - `one_at_a_time`: the runner scales to 1, restarts, then scales to the variant's replicas, so each pod after the
    first starts beside a Ready one.
  - It is allowed only with fixed replicas of 2 or more and no autoscaler (an autoscaler already adds pods one at a
    time). Anything else is refused with the variant's name.
- **The diagnostic experiment, `experiments/two-pod-stall.yaml`:**
  - real at 2 replicas, with validate-sim's trace, pattern, seed, warm-up and KV capacity
  - variants `together`, then `one-at-a-time`
  - the evidence: both GPU logs, the pods' logs (graph capture, and vLLM's throughput every 10 s) and the replay's
    calls. No `pod_stall_seconds`, which would stop the run at the first stalled variant (Claude, while coding).
  - about 1-1.5 h
- **Reading the result:**

  | together | one_at_a_time | Then |
  |---|---|---|
  | stalls | runs well | Start order is the cause. Fix: real pods start one at a time wherever they start |
  | stalls | stalls, shared usage up | Memory is the cause whatever the order. Fix: a smaller footprint, first `capture_sizes: [1, 2]` (P4.13: 0.04 GiB per pod) |
  | stalls | stalls, shared usage flat | The cause is elsewhere: one more approach, then stop and report (rule 8) |
  | runs well | runs well | Not reproduced: reported to the user before anything else |
