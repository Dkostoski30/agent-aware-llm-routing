# P4.13: CUDA-graphs spike, measuring only

Added 2026-11-22. Placed by the user on 2026-11-18: after P3.13c, before P4.7. Since 2026-11-19 every Phase 4 row is
built, with no slip order. Why: each call makes only 17-61 tokens, so its time is almost all decode. P2.8a measured
150 ms per token with the adapter on 1 pod and 311 on 2 (plain model 62 and 81), and the user's chat runs were ~270.
Every vLLM pod runs `--enforce-eager` (`infra/charts/vllm/templates/deployment.yaml`, `infra/local/vllm-common.sh`),
kept for VRAM with 2 pods in 4 GB. Dropping the adapter is ruled out: the plain model scored 33/98 held-out against
the adapter's 97-98/98 (`experiments/log.md`).

Read in the code before planning (Claude, 2026-11-22):
- vLLM v0.31.0 (the pinned image, `engine/arg_utils.py`) has `--cudagraph-capture-sizes` and
  `--max-cudagraph-capture-size`, so capture can be limited to batch sizes 1 and 2.
- `config/compilation.py` `CUDAGraphMode` has `FULL_DECODE_ONLY`, which does not need torch.compile's piecewise mode,
  so graphs without torch.compile are possible in principle. The source alone does not show whether this works with
  LoRA.
- Nothing mounts torch.compile's cache in a pod, so a compiled pod compiles again on every start. That costs cold start
  (sim `startup_duration` 140 s, P2.8b).
- `make calibrate`'s grid is fixed to the lora/plain pair and refuses a LoRA in `plain` (`sim/calibrator/config.py`).
  Its call code (`measured_call`, `closed_loop`, the prompts, the stats) can be reused unchanged.
- `make vllm-deploy` passes the profile's whole `model` section to the chart. `drain.py`'s `pool_command` already
  changes one value of the live release with `helm upgrade --reuse-values`.

Decisions (the user, 2026-11-22):
1. Measure real (0.6B + LoRA) at 1 and 2 pods, and demo (1.7B) at 1 pod. (Offered: real only; demo only.)
2. Three variants: `eager` (today), `graphs` (torch.compile, graphs at sizes 1 and 2), `graphs-nocompile`
   (`FULL_DECODE_ONLY`, compile mode 0, sizes 1 and 2). A variant that does not start is a finding, not retried.
   (Offered: eager and graphs only.)
3. In the repo: a profile key, an experiment file, a make target, tests first. (Offered: a scratch script and a log
   entry only.)
4. Speed only, no go/no-go. Correctness is left to whichever task adopts graphs. (Offered: go/no-go on each demo
   graphs variant.)

Decided while planning (Claude, stated to the user):
- Profile key `model.cuda_graphs: {mode, capture_sizes}`, with `mode: eager` in real, real-plain and demo. sim is
  left out, since it deploys no vLLM pods. The chart refuses a missing key. With `eager` it renders `--enforce-eager`
  exactly as today; a `helm template` test holds the args unchanged for all three profiles. (Planned as
  `{enabled, compile, capture_sizes}`; changed while building to one `mode` of `eager`, `compiled`, `decode_only`,
  since the three variants are three states, not two independent switches.)
  `infra/local/vllm-common.sh` (the Docker path from P0.3-P0.5) keeps `--enforce-eager` and is not touched.
- No profile adopts graphs here. Whether one does is decided by the user with the numbers.
- The spike's code sits in `sim/calibrator/` beside `calibrate.py` (same `PYTHONPATH`), so the reused code is
  imported, not copied.
- Per profile, the script deploys it at 1 pod, then for each variant does a `helm upgrade --reuse-values` of
  `model.cuda_graphs` (the new pods' start is timed), warms up as `make calibrate` does, and measures the 1-pod cells.
  For real it then scales to 2 (the added pod's start is timed, as autoscaling adds one) and measures the 2-pod
  cells. At the end it restores `make vllm-deploy PROFILE=real`.
- Cells: concurrency 1 and 2 per pod, a 1,024-token prompt in `partial` cache mode (an agent step extending its
  history), 64 tokens with `ignore_eos`, 20 calls per cell. These are calibrate's settings, so its numbers compare with
  P2.8a's.
- What is recorded per variant and profile:
  - created → Ready and Ready → first answer for each started pod
  - `nvidia-smi` memory used once every pod is Ready
  - vLLM's own startup log lines for graph capture (seconds, GiB) and the KV cache size in tokens, so a changed
    4,384 / 7,312 shows
  - TTFT and per-token p50 and p95 per cell
  - "fits": every pod Ready within the deploy timeout and every call answered
- A pod that is not Ready within the timeout (a named constant in the script, like `VLLM_DEPLOY_TIMEOUT`) or that
  crashes: its variant is recorded as not fitting, with the pod's last log lines, and the script goes on to the next
  variant.
- The host check is `make calibrate`'s (Performance plan, no sleep on AC).
- Outputs, stamped with the experiment file's hash (D11): `experiments/results/cuda-graphs-<hash>-cells.csv`,
  `-starts.csv` and `.meta.json`.
- Run time about 2 h with the laptop idle.

## Built (2026-11-22, after "go")

- `config/real.yaml`, `real-plain.yaml`, `demo.yaml`: `model.cuda_graphs: {mode: eager}`. `helm template` of the vllm
  chart is byte-identical to before for all three (checked against renders saved before the edit).
- `infra/charts/vllm/templates/deployment.yaml`:
  - refuses a missing key, an unknown mode, and off eager capture sizes that are not ascending whole numbers from 1
  - eager renders `--enforce-eager` in its old place
  - `compiled` renders `--cudagraph-capture-sizes 1 2` there
  - `decode_only` also renders `--compilation-config={"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY"}`
  - eager ignores leftover sizes, since `--reuse-values` merges maps
- `infra/checks/test_cuda_graphs_chart.py` (23 tests), reusing `test_drain_chart.py`'s helpers.
- `sim/calibrator/cuda_graphs.py`:
  - imports make calibrate's `LiveCluster`, `LivePods`, cells, warm-up, host check and stats unchanged, plus
    `config.py`'s `_count`, `_levels` and `_cache`
  - each variant empties the pool (`helm upgrade --reuse-values --force-conflicts --set replicas=0 --set-json
    model.cuda_graphs=...`, then waits for the pods to go), so every variant's first pod starts alone; it then scales
    to each pod count
  - a variant fails to fit on `CalibrationError` (a failed call, or a pod still slow after warm-up) or
    `CalledProcessError` (kubectl's wait timed out); the meta records it with each pod's state and last 40 log lines,
    and the run goes on
  - graph lines kept in the meta: any line naming cudagraph, CUDA graph or graph capture
- `sim/tests/test_cuda_graphs.py` (36 tests). 15 mutants of the module, 14 killed; the survivor, a "last match" rule
  for log lines that no test needed, was removed (one container start prints each line once).
- `experiments/cuda-graphs.yaml`; `Makefile` `cuda-graphs`.
- Outputs: `experiments/results/cuda-graphs-<hash>-cells.csv` and `-starts.csv` (renamed from `.partial` at the
  end), then `.meta.json` last. A rerun with the meta does nothing.
