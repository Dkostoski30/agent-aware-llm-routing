# P4.2: New runs go to the pods that just turned Ready

Added 2026-11-19. PLAN.md's row says "new runs prefer the newest pod"; decided while planning (the user, 2026-11-19):
all pods in their warm-up window, not only the newest, since KEDA adds several at once (P3.9b: 1 -> 4).

Why the default picker needs it, from results already in the repo (Claude, read-only, 2026-11-19): in the sim
autoscale replays of P3.9b (3fb2040041ef) and P3.10 (4dab13427b51, both variants), after the new pods turned Ready,
about 4 of the next 10 runs' first calls still went to the one old, busy pod. The likely cause: prefix-cache-scorer
(weight 3) favors the pod that holds the shared system prompt, against queue-scorer and kv-cache-utilization-scorer
(weight 2 each). With affinity on, the old runs stay pinned there too, so the old pod stays the busiest.

Read in source before planning (2026-11-19):
- llm-d-router v0.11.0: the picker's candidates are Ready pods only (`controller/pod_reconciler.go`). `EndpointMetadata`
  has no creation or Ready time. A plugin that implements `datalayer.Registrant` gets Kubernetes events for a GVK through
  `k8s-notification-source` (`cmd/epp/runner/runner.go` calls RegisterDependencies on every plugin;
  `datalayer/k8s_bind.go` watches through the manager's cache), as upstream's topology extractor does for Pods.
- The picker's Role in the pinned chart (llm-d-router-gateway, digest in versions.md) already grants pods get, watch and
  list. `k8s.io/apimachinery` v0.36.4 is already a direct requirement of `gateway/go.mod`. No new dependency, no new RBAC.

# P4.2: warm-up routing

Goal:
With routing.warmup on, a run's first call goes to the pods that turned Ready within the last routing.warmup_seconds,
while they have room, so pods KEDA just added take new runs at once instead of the old pod the prefix cache favors.

Depends on:
P4.1 (committed 4f2bb53)

Files allowed:
gateway/runrouter/warmup.go (new), gateway/runrouter/warmup_test.go (new), gateway/runrouter/plugin.go,
gateway/runrouter/plugin_test.go, gateway/runrouter/flags.go, gateway/runrouter/metrics.go (the counter's help),
config/real.yaml, config/real-plain.yaml, config/demo.yaml, config/sim.yaml,
infra/routing-values.sh, loadgen/tests/test_routing_values.py,
loadgen/load_generator/experiment.py (PROFILE_ONLY_KEYS), loadgen/tests/test_experiment.py,
loadgen/load_generator/warmup.py (new), loadgen/tests/test_warmup.py (new), Makefile (make warmup-report),
experiments/warmup.yaml (new),
experiments/log.md, PLAN.md (P4.2 row), docs/task-cards/58-P4.2-warm-up-routing.md

Interfaces / outputs:
- config, every profile: routing.warmup_seconds (first guess 120: one gap between bursts of the burst pattern, so a pod
  added during a burst is still new when the next one comes); routing.warmup_queue_threshold (first guess 1, as
  routing.overload_queue_threshold on sim: a new pod with more calls waiting than this has no room, so a burst can't
  pile onto a cold pod). routing-values.sh checks both (whole numbers; seconds positive, threshold 0 or more) and passes
  them as warmupSeconds and warmupQueueThreshold; flags.go refuses missing, null or out-of-range ones.
- Pod Ready times: the plugin registers a Pod NotificationExtractor (k8s-notification-source). For each pod whose Ready
  condition is True it keeps that condition's lastTransitionTime; a delete or a pod not Ready drops it. A pod with no
  Ready time known counts as old. The watch runs whatever the flag, and each Ready time the plugin learns is logged
  once ("Pod ready", pod, readyAt), so the report has it for a variant with warmup off too.
- Filter, flag on: a call with x-step 1 (a run's first call; it works without affinity) and no live pin is judged.
  New = a candidate whose Ready time is within warmup_seconds of now. If at least one candidate is new, at least one is
  not, and at least one new one has waiting <= warmup_queue_threshold (the picker's metrics for the pod), the call
  gets those new pods with room; the scorers choose among them. Otherwise the call is not changed. All candidates new
  (right after make up) changes nothing. The verdict goes on the request for PreRequest.
- Precedence: while some candidates are new and some not, warm-up decides a run's first call, with room or without
  (warmup-full: every candidate, the scorers choose); least_work_first and least_context_first judge first calls only
  when no pod is new. The overload guard and parallel spill judge pinned calls only, so they never see a first call.
- PreRequest: reason warmup or warmup-full in the "Run call picked" line and the decisions counter, whatever affinity,
  with newPodAge and newPodQueue (each new candidate's seconds since Ready and waiting count, by endpoint name); the run
  is pinned to the pod chosen when affinity is on.
- make warmup-report RESULT=experiments/results/warmup-<hash> reads each variant's replay JSONL and picker log (the
  window as the plugin loaded it, the vLLM pods' "Pod ready" lines) and writes <RESULT>-warmup.csv, one row per
  variant: the step-1 calls sent while some pod was new, how many went to a new pod, how many to an old one, how many
  of those the picker judged warmup-full, how many failed; and <RESULT>-warmup-pods.csv, one row per vLLM pod that
  turned Ready after the replay started: its Ready time, first call and first step-1 call (seconds from the replay's
  start), the step-1 calls that went elsewhere between its Ready time and its first one, and those it got in its
  window. A window holds both ends, as the plugin's. It refuses a variant on the default picker, which logs no Ready
  times.
- experiments/warmup.yaml: profile sim, P3.9b's trace, pattern burst, seed 6, warm-up 4 runs, KEDA on remaining work,
  two variants, warmup-off {plugin: true, affinity: true, warmup: false} then warmup-on {..., warmup: true}.
- experiment.py: warmup_seconds and warmup_queue_threshold are profile-only keys, which a variant may not set.

Notes:
- Ready time, not "first seen by the plugin" (decided 2026-11-19): exact, and a picker restart does not make every pod
  new. A pod whose Ready flips False and back gets a new Ready time and is new again; stated, not handled.
- Real pods (not shown here; P4.5 runs real 1<->2): a real pod's first call is slow (14.3 s median TTFT, folded into
  the simulator's 140 s startup, config/sim.yaml), and in P4.1 one fresh pod took ~50 s before its engine counted the
  calls sent to it. Warm-up sends new runs into exactly that. The room cap bounds how many; whether it helps on real
  pods is P4.5's question.
- Off in every profile until an experiment turns it on, as every rule since P3.7b.
- The room cap reads the picker's last read of each pod's metrics (every 50 ms), so first calls that arrive within one
  read, as a burst's 5 runs do, all see the same queue and may all go to one new pod. Stated, not counted against
  (P3.6 counts a group's calls in flight for this reason); the replay shows whether it matters.
- Tests first: Ready-time bookkeeping (Ready, not Ready, delete, no condition, a Ready time older than the window); the
  filter table (flag off; step 2 or later; live pin; no new pod; all new; new over the threshold; two new pods, one with
  room; a pod with no Ready time); the precedence over least work; the PreRequest reason; flags' refusals; the
  routing-values checks; the report on hand-written JSONL and picker lines.
