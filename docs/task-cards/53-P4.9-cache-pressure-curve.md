# P4.9: Cache pressure, measured on the replays we have

Added 2026-11-16 (Claude's proposal, planned at the user's request). P3.7 and P3.7b closed red with "cache loss under this burst is capacity". The question here: is there one number, known while runs are active, that says when a pool of pods is past that point?

Cache pressure at a moment = the context the live runs hold / the KV cache of the pods. A run is live from its first call's start to its last call's end and holds the prompt tokens of its latest call; the pods hold replicas x `kv_capacity_tokens_per_pod`.

How it differs from what the repo has: `tokens_on_pod` and `over_kv_limit` (results.py, P2.4) count the calls in flight on one pod, after the fact. Pressure counts runs, also between their calls, over the whole pool, which is what the run tracker can know live (P4.10). vLLM's own `vllm:kv_cache_usage_perc` reads what is in use, and did not separate calls that lost their cache from calls that kept it (P3.7b: 0.69 against 0.66).

Spike 2026-11-16 (a script outside the repo, read-only, as P3.7b's spike). Nine real-pod files, 2 pods x 4,384 tokens, 2,761 later-step calls: `baseline-reversed-694f06470e98` (default, round-robin), `validate-sim-5593507542a4-real-2pods`, `routing-burst-b36ab68af75c` and `routing-burst-reversed-e19c9624b221` (default, plugin), `routing-faster-d7acfd33b019` and `routing-faster-reversed-9a6c4680fec5` (default).

| pressure | calls | first token, median | cached share |
|---|---|---|---|
| under 0.75 | 1,046 | 0.4-0.5 s | 0.82-0.89 |
| 0.75-1.0 | 146 | 0.8 s | 0.78 |
| 1.0-1.25 | 79 | 0.8 s (p90 13.4 s) | 0.74 |
| 1.25-1.5 | 140 | 6.2 s | 0.51 |
| 1.5-2 | 212 | 9.0 s | 0.41 |
| 2-3 | 739 | 14.0 s | 0.36 |
| over 3 | 399 | 26.6 s | 0.35 |

In the burst files 81% of the default picker's later-step calls and 77% of the plugin's were over 1, and the two pickers gave the same curve.

What the spike does not show:
- It read `ts_start`, the wall clock, which results.py never reads because it moved against the monotonic clock under WSL2 (P2.2a). This task times calls as results.py does, so the numbers may move.
- It counted every run in the files, the discarded warm-up runs too.
- Pressure and the queue rise together, so first-token time holds both. The cached share is the part a queue alone does not explain.
- The bend is somewhere between 0.75 and 1.25, not at 1: the two steady files already slow at 0.75-1.0.
- A rough what-if of the obvious cure, one run per pod at a time, came out slower than what was measured (mean run 506 s against 214 s). Admission is not planned.
- The effect is published (CONCUR, MARS, XPerf: `docs/thesis/sources.md`, none read yet; MARS's title names KV thrashing under GPU memory limits, the closest to this). What this adds is the measurement on two small pods and, in P4.12, pods scaled on it.

Decided while planning (the user, 2026-11-20):
- The files: every real-pod variant with a fixed pod count in `experiments/results/`, 28 variants in 14 files, a rule rather than the spike's pick; `experiments/pressure.yaml` lists them. Left out by the rule: validate-sim's simulated variants and autoscale-real's cpu variant (1 to 2 pods during its replay, refused as autoscaled).
- The discarded warm-up runs are live (the pods hold their context) but give no row.
- A run whose call failed stops being live when that call was sent; how many runs ended so is printed per variant.
- Claude's choices: a fanned-out step's calls count once per run (the largest prompt); a call counts itself; a run that ended as a call began has left (as `tokens_on_pod`); the cached share per bucket is the mean of the calls' shares; the planned starts come from today's profile pattern at the file's seed, whose numbers have not changed since the first of these files (`git log -p config/real.yaml`), and a run past the pattern's count is refused. The graph is pooled only, two panels (first token median and p90 on a log axis; cached share), drawn by `graph.render_pressure`, so `graph.py` and `config/report.yaml` changed as the card allows; `test_report_config.py`'s fixture gained the new required key.

# P4.9: Cache pressure, measured on the replays we have

Goal:
One command reads the real-pod replays already in experiments/results/ and writes, for every later-step call, the cache pressure at its
start beside its first-token time and cached share: a CSV, a graph and a printed table. No cluster.

Depends on:
P2.5 (results.py), P3.7b (the files)

Files allowed:
loadgen/load_generator/pressure.py (new), loadgen/load_generator/results.py (only to share its call timing), loadgen/load_generator/graph.py,
loadgen/load_generator/report_config.py, config/report.yaml (the bucket edges), loadgen/tests/test_pressure.py (new), loadgen/tests/,
experiments/pressure.yaml (new), Makefile (make pressure), experiments/results/, experiments/graphs/, experiments/log.md,
PLAN.md (P4.9 row), docs/task-cards/53-P4.9-cache-pressure-curve.md

Interfaces / outputs:
- experiments/pressure.yaml names the experiments to read by stem. Each one's .meta.json gives the trace, pattern, seed,
  kv_capacity_tokens_per_pod, the variants and their replay files. Results carry this file's hash (D11).
- make pressure -> experiments/results/pressure-<hash>.csv, one row per later-step call that has a first token: experiment, variant, run,
  step, pressure, ttft_ms, cached share; experiments/graphs/pressure-<hash>.png; and a printed table per variant and pooled: per bucket
  the calls, first-token median and p90, and cached share.
- Pressure of a call: over the runs live at the call's start, the prompt tokens of each run's latest call begun by then, divided by the
  variant's replicas x kv_capacity_tokens_per_pod. Times rebuilt as results.py rebuilds them, never ts_start.
- Bucket edges in config/report.yaml with a comment: fixed before the first run on rebuilt times, the spike's edges.
- A variant on a sim profile is refused with the reason: the simulator does not model KV admission (P3.7b).

Notes:
Tests first: a call's pressure from known lines (a run before its first call and after its last adds nothing; a run between calls adds
its latest prompt; two runs on one moment add up), the buckets, a refused sim variant, the same CSV twice. Decide in the plan and state
it: whether the discarded warm-up runs count as live (they hold KV) and whether a failed call's run does. If the rebuilt times show no
bend, record that: no edge moves to make one (rule 8). D11: the experiment files are read, never edited (an edit changes their hash).

Done when (I run this myself):
