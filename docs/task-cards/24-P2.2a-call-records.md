# P2.2a: The agent records every LLM call

P2.2 (call recorder) is split in two (2026-11-01): P2.2a records each call's measurements with the run in Redis,
P2.2b turns recorded runs into trace.v1 JSONL. Decided 2026-11-01 with the user: no TTFT in agent traces. Agent calls
stay non-streaming (D6), so the agent only sees the whole reply; ttft_ms stays optional in trace.v1, the replayer
(P2.3) streams its own calls and records it, and P2.8 measures TTFT for the simulator.

# P2.2a: The agent records every LLM call

Goal:
For every LLM call of a run, the agent saves the call's measurements with the run in Redis (D7): step, start time,
duration, gap since the previous call, prompt / completion / cached prompt tokens, and the pod that served it.

Depends on:
P2.1a-3 (the tool set the recorded runs use)

Files allowed:
agent/agent_runtime/ (llm.py, loop.py, store.py, app.py), agent/tests/, infra/charts/vllm/templates/deployment.yaml
(one vLLM flag), infra/manifests/inference-gateway.yaml (only if the pod comes from a response header),
docs/task-cards/24-P2.2a-call-records.md

Interfaces / outputs:
- Per call: step, ts_start (ms since epoch), duration_ms, gap_before_ms (end of the previous call to the start of
  this one: tool time, D9; 0 for step 1), prompt_tokens, completion_tokens, cached_tokens, pod. Field names follow
  trace.v1 where it has them.
- Tokens from the response's usage. cached_tokens from usage.prompt_tokens_details.cached_tokens, which vLLM fills only
  with --enable-prompt-tokens-details (to be confirmed for the pinned vLLM in plan mode). It is the per-call cache hit
  that P2.6's badges and P3.3's affinity check need.
- pod: settled in plan mode by a short spike, in this order: (1) a response header the gateway adds with the chosen
  endpoint (AgentgatewayPolicy, if agentgateway can expose it), mapped to the pod name; (2) the gateway access log's
  endpoint joined by run-id and step at export time (P2.2b). The pod name, not the IP: IPs change on restart.
- Saved in Redis next to the run (e.g. thesis:run:<id>:calls), same TTL, written in the same transaction as the step,
  so a record and its calls never come from different steps.
- The "llm call" log line gains the same fields (D12: run-id on every run line).

Notes:
Tests first with the mocked LLM: gap_before_ms is 0 on step 1 and the tool time on later steps (a fake clock), token
fields come from usage, a reply without usage or prompt_tokens_details leaves the field out instead of writing 0, the
calls list has one entry per call and is saved with the step. Invalid calls are LLM calls too and are recorded. The
vLLM flag changes the pods' command line, so make vllm-deploy runs again (both profiles).
