# P2.2a: The agent records every LLM call

P2.2 (call recorder) is split in two (2026-11-01): P2.2a records each call's measurements with the run in Redis,
P2.2b turns recorded runs into trace.v1 JSONL. Decided 2026-11-01 with the user: no TTFT in agent traces. Agent calls
stay non-streaming (D6), so the agent only sees the whole reply; ttft_ms stays optional in trace.v1, the replayer
(P2.3) streams its own calls and records it, and P2.8 measures TTFT for the simulator.

Decided 2026-11-02 with the user in plan mode: the pod comes from vLLM, not the gateway. vLLM v0.31.0 sets every
non-streaming reply's system_fingerprint to --fingerprint-value under --fingerprint-mode=custom
(vllm/entrypoints/generate/api_router.py, generate/base/serving.py), and the chart passes $(POD_NAME) from the downward
API, so no AgentgatewayPolicy spike and no change to infra/manifests/inference-gateway.yaml: a gateway header would give
only ip:port, which the agent could name only through the Kubernetes API (a new dependency and RBAC), and the access-log
join would leave the pod out of Redis. --enable-prompt-tokens-details is confirmed in the same source
(vllm/entrypoints/launchers/cli_args.py, default off); with it on, a cache miss reads cached_tokens 0 (corrected after
the review, below). A call that gets no reply (HTTP error, timeout, a body that is not a chat completion) gets no
record: one record per reply, invalid and cut-off replies included, so the records match the steps GET /runs/{id} shows;
the record's step still counts the call and its error says why. A usage field of the wrong type makes the body not a
chat completion. Each record also keeps the expected_steps its call carried (trace.v1 requires it; D13 changes it
mid-run later). gap_before_ms is the time between calls, so it holds the step's Redis save as well as the tools. The
calls stay out of GET /runs and the run events (run-events.v1 is P2.6's). The existing tests change only where the step
callback and store.save gain the calls (test_agent_loop's on_step helpers, ScriptedLLM's optional usage and fingerprint,
test_app's MemoryStore, test_store's save call), in a separate commit before this card's (PLAN.md rule 5).

Decided 2026-11-02 with the user, when the session in ~/thesis took the card over from the worktree ~/thesis-p2.2a:
ChatReply's four new fields default to None, since experiments/finetune_data.py's scripted LLM builds a ChatReply from
the message and finish reason alone and failed with a TypeError (experiments/tests); a scripted reply has no usage and
no pod, which None already means. finetune_data.py is unchanged.

Decided 2026-11-02 with the user after the fresh-eyes review. The done-when's cache check compares a step with the
step before it on the same pod: "cached_tokens > 0 on step 2" passed from the shared system prompt on any warm pod and
failed when step 2 went to the other cold pod after make up. Step 2 then holds step 1's whole prompt but its last,
partly filled KV block; vLLM's block is 16 tokens (CacheConfig.DEFAULT_BLOCK_SIZE; vLLM logs "Setting kv cache block
size" when it picks another, and the real pods' logs have no such line). Fixed in this card, tests first and each new
test seen catching a deliberate bug: a wall clock set back during a call moves ts_start but not durations or gaps;
null usage, counts, cached_tokens and system_fingerprint are left out like missing ones; a cached_tokens, usage or
system_fingerprint of the wrong type fails the run; _optional is generic, so mypy checks each field's type; app.py
takes its timestamps from the loop's SYSTEM_CLOCK instead of a copy of it. Corrected: with
--enable-prompt-tokens-details a cache miss reads cached_tokens 0, not a missing field (v1/engine/output_processor.py
starts the count at 0; chat_completion/serving.py drops prompt_tokens_details only when it is None; read in the
pinned image). Reported, not changed: a server without --fingerprint-mode=custom (local containers, perhaps the
simulator in P2.7) sends vLLM's default fingerprint vllm-0.31.0-<hash8>, which the agent would save as a pod; an
empty pod or a negative count passes the type check; trace.v1 has no cached_tokens (additionalProperties false) and
requires prompt and completion tokens a record can lack. P2.2b writes trace.v1 and gets its contract test, so it
settles those.

# P2.2a: The agent records every LLM call

Goal:
For every LLM call of a run, the agent saves the call's measurements with the run in Redis (D7): step, start time,
duration, gap since the previous call, prompt / completion / cached prompt tokens, and the pod that served it.

Depends on:
P2.1a-3 (the tool set the recorded runs use)

Files allowed:
agent/agent_runtime/ (llm.py, loop.py, store.py, app.py), agent/tests/, infra/charts/vllm/templates/deployment.yaml
(three vLLM flags and the POD_NAME env, decided 2026-11-02), docs/task-cards/24-P2.2a-call-records.md,
experiments/log.md

Interfaces / outputs:
- Per call: step, ts_start (ms since epoch), duration_ms, gap_before_ms (end of the previous call to the start of
  this one: tool time, D9; 0 for step 1), expected_steps (the call's x-expected-steps), prompt_tokens,
  completion_tokens, cached_tokens, pod. Field names follow trace.v1 where it has them.
- Tokens from the response's usage. cached_tokens from usage.prompt_tokens_details.cached_tokens, which vLLM fills only
  with --enable-prompt-tokens-details (confirmed in v0.31.0's source; a miss reads 0). It is the per-call cache hit
  that P2.6's badges and P3.3's affinity check need.
- pod: the reply's system_fingerprint, which the vLLM chart sets to the pod name (decided 2026-11-02, above). The
  pod name, not the IP: IPs change on restart.
- Saved in Redis next to the run (e.g. thesis:run:<id>:calls), same TTL, written in the same transaction as the step,
  so a record and its calls never come from different steps.
- The "llm call" log line gains the same fields (D12: run-id on every run line).

Notes:
Tests first with the mocked LLM: gap_before_ms is 0 on step 1 and the tool time on later steps (a fake clock), token
fields come from usage, a reply without usage or prompt_tokens_details leaves the field out instead of writing 0, the
calls list has one entry per call and is saved with the step. Invalid calls are LLM calls too and are recorded. The
vLLM flag changes the pods' command line, so make vllm-deploy runs again (both profiles).

                                            on two pods the check does not apply: make smoke again)
